# THE OBJECTIVE'S COUNTERS, EACH AGAINST THE TREND GATE'S KEYS FOR IT.
#
# `<objective counter> <gate key>`, one pair a line, several lines for a
# counter that is a sum. The gate's key carries its golden's prefix, so
# `work_jsonbench` is the row welfare calls `decode_instructions`.
#
# WHY THE LINK IS WRITTEN DOWN RATHER THAN DERIVED. welfare renames on the
# way in and, for the memory terms, also sums: `peak_of` adds the arena,
# held and perm peaks, so a `*_peak_bytes` term is a derived quantity and no
# row anywhere carries its value. A join on values was measured before this
# file was written and cannot work — of the five counters, one has no row
# holding its number at all (`run_peak_bytes` is a sum of three) and the
# arena peak matches several goldens at once (2,097,152 is
# `arena_peak_bytes` in four of them).
#
# tests/the_objective_reads_what_the_gate_watches.rs replays this file: it
# sums each counter's keys out of the goldens the trend gate walks and
# asserts the total is what `welfare --counters` prints, for all five and no
# others. A rename on either side, a pool added to `peak_of`, or a counter
# joining the objective turns that spec red rather than quietly unlinking a
# term.
#
# What reads it is the trend gate's `shifted?`: a golden row whose objective
# counter's welfare baseline moved in the same diff is a re-basing, and a
# re-basing is neither better nor worse.
#
# 2026-09-06: the count in the two lines above said 27 and the file had held 28
# since livebench joined on 2026-09-05. 2026-09-07: it said 28 and the file has
# held five since the gavel below cut the runtime side to one program the day
# before. Both times the spec replays the file rather than a number, so nothing
# was ever unchecked; the prose was, twice, and CLAUDE.md carried the second
# one on into a session that computed a trade over the wrong model.

# what compiling costs. The instruction term sums TWO OF THE THREE compile
# paths. `kanso check` routes a single file by its content, and the three
# routes are three different compiles: a DIRECTORY is a module and takes
# compile_module_inner, a file of bare STATEMENTS is an entry and takes
# compile_parsed_entry, and a file of DEFINITIONS alone is a library and takes
# compile_library. Until the entry vein opened on 2026-09-08 the objective
# could see only the first.
#
# THE LIBRARY ROW IS LEFT OUT BY MEASUREMENT, not by oversight.
# bench/entry_corpus and bench/library_corpus name the identical ten imports,
# and under callgrind the two compiles are the same measurement:
#
#     frame                     module        entry       library
#     kanso::main           49,226,188  163,918,585  164,230,408
#     load_dependencies     29,179,760  112,141,854  112,163,002
#     compile_module_inner  41,345,039  100,795,947  100,804,487
#     check_merged_after..  17,585,954   62,110,471   62,242,504
#     infer::infer          10,931,355   36,679,783   36,496,937
#
# 311,823 apart out of 164M, which is 0.19%, and their dependency loads agree
# to 21,148, which is 0.019%. The term is already 66% dependency loading --
# 29.2M for the module corpus's four imports and 112.1M for the entry corpus's
# ten -- so admitting the library row would count that same 112.1M a third
# time and weight loading three to one against the compiler's own passes, for
# a dimension the entry row already carries. The module row is redundant with
# neither: four imports against ten, 49.2M against 164M.
#
# bench/library_instructions_golden.txt is unaffected and still fails CI when
# it moves. A vein the objective does not weigh is still a vein.
compile_instructions compile_instructions
compile_instructions entry_instructions
compile_allocs compile_allocs
compile_peak_bytes compile_peak_bytes
