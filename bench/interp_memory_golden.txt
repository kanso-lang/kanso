# What an INTERPRETED run holds, and the traffic it makes holding it.
#
# `KANSO_COUNTERS=1 kanso run interp_corpus --interp`, read off the same
# counting allocator the compiler's own row reads. The interpreted engine is a
# deployment rather than a stage of one -- the program is parsed, inferred and
# then EXECUTED in this process, and nothing is emitted -- so these two rows
# cover the front end and the interpreter together, which is what an
# interpreted run actually costs. The compile veins cannot see either number:
# they run `kanso check`, which stops before anything is executed.
#
# TWO DIMENSIONS, NOT ONE. interp_allocs is TRAFFIC, what the run asked the
# allocator for and gave back; interp_peak_bytes is RESIDENCY, the most it held
# at once. A thunk allocated and forced inside one beat moves the first and not
# the second, which is why both are here.
#
# BOTH BELONG TO THE RUSTC THAT BUILT THE COMPILER, the way compile_peak_bytes
# does: a HashMap's growth schedule and a Vec's doubling are the standard
# library's, and the interpreter is Rust. So the rows are exact for the host
# the measured-on line names and any other host refuses to compare rather than
# fuzzing. Clay ruled tolerance bands away on 2026-08-24.
#
# WHY IT EXISTS. Clay ruled on 2026-09-16 that the objective becomes a
# development welfare, a production welfare and a meta over them, and named the
# interpreted engine's own order: "start-time is vastly more important than
# speed which is more important than memory usage." This is the last of the
# three. It is an exact vein of its own and not yet an objective term, the way
# `.text` is under the 2026-09-05 ruling.
#
# 2026-09-16 (the vein opens): three runs of one binary read these two rows
# identically before the fixed-seed change and identically after it, which is
# the check on what that change touched -- a probe sequence moves how much work
# a table does and not how many bytes it asks for. The instruction row beside
# this one moved 10.40% across the same change and these did not.
#
# 2026-09-16: CI's first sitting read BOTH ROWS EXACTLY as this container did,
# interp_allocs 5,313,431 and interp_peak_bytes 933,202, across rustc 1.94.1
# here and 1.98.1 there. That is worth writing down rather than assuming: the
# instruction row beside these diverged 2.18% between the same two hosts, and
# these did not move at all. What a run ASKS the allocator for is the
# program's own shape; what it COSTS to ask is the toolchain's.
#
# 2026-09-17 (kanso#1462): interp_allocs 5,313,431 -> 5,313,434, a RISE of 3.
# interp_peak_bytes came back 933,202, byte-identical, and interp_instructions
# 2,178,559,085, on the row. Three allocations out of five million is the
# Why three and not zero is not measured; the run's shape did not change, since
# peak bytes and the instruction row both came back on the nose.
#
# 2026-09-17, kanso#1486 on the tree merged with kanso#1462. CI reads
# 5,313,332 against main's 5,313,434, a fall of 102. The front end allocates
# on the interpreted path too, and running the alias fixpoint once instead of
# twice is 102 fewer allocations on this program. interp_peak_bytes is
# unchanged at 933,202: the fixpoint's working sets were never the high-water
# mark.
#
# 2026-09-18, kanso#1511 on the tree merged with main, CI's sitting.
# 5,313,332 -> 5,313,348, a RISE of 16 (+0.0003%).
# The predicate's answer is a set of owned names, built once. Sixteen
# allocations is what that set costs on this program.
#
# 2026-09-18, re-merged onto main after kanso#1510. THE VALUE BELOW IS MAIN'S,
# carried forward, and the branch's own reading above it stands as history.
# The six compile-side goldens beside it were carried forward because
# kanso#1510 moved them; this one did not conflict, so the branch's +16
# survived alone and the trend gate read a PURE REGRESSION -- one row worse
# and nothing better, because the falls that sat beside it are now main's.
# Every row on this branch is main's, so CI measures the merged tree in one
# piece and the real sixteen comes back with whatever moves beside it.
#
# 2026-09-18, kanso#1511 on the tree merged with main after kanso#1510,
# CI's sitting. 5,313,332 -> 5,313,348, a RISE of 16
# (+0.0003%). THE ONE ROW THAT REPRODUCES. +16 on both rounds, against two different
# bases: the predicate answers with a set of owned names, built once, and
# sixteen allocations is what that set costs on this program.
#
# 2026-09-18, kanso#1516. ROUND ONE IS DELIBERATELY RED ON BOTH ROWS, for the
# reason the instruction golden gives: this host cannot compare, so the values
# below are main's and CI's sitting replaces them.
#
# Measured here, as evidence of direction and size: interp_allocs
# 5,310,694 -> 4,985,431, a FALL of 325,263 (-6.12%), and interp_peak_bytes
# 933,280 -> 942,308, a RISE of 9,028 (+0.97%).
#
# THE TWO DIMENSIONS GO OPPOSITE WAYS AND BOTH ARE THE SAME CHANGE. The traffic
# falls because `eval_ident` no longer builds an `Rc<str>` for every reference
# it returns -- 325,412 of those on this corpus, against a measured fall of
# 325,263. The 149 they differ by is what the table costs: a `String` per
# distinct name plus the map's own growth, and how it splits between those two
# is not measured. The residency rises because that table is held for the whole
# run. It is what the traffic bought, and it is the trade to read here rather
# than either row alone.
#
# The thunk counters are byte-identical across the change -- 1 alloc, 6 forces,
# 1 eval -- so nothing semantic moved.
#
# 2026-09-18, kanso#1516 on the tree merged with main, CI's sitting.
# interp_allocs 5,310,696 -> 4,985,433, a FALL of 325,263 (-6.1247%).
# interp_peak_bytes 933,182 -> 942,210, a RISE of 9,028 (+0.9674%).
#
# BOTH DELTAS ARE THE CONTAINER'S TO THE UNIT. This box read 5,310,694 ->
# 4,985,431 and 933,280 -> 942,308: different absolute values, because these
# rows belong to the rustc that built the compiler, and the SAME -325,263 and
# +9,028. That is what a counter of operations rather than of a host looks
# like, and it is why the instruction row's two readings could be trusted to
# agree as closely as they did.
#
# 2026-09-18, kanso#1517 (stacked on kanso#1516). ROUND ONE IS DELIBERATELY RED
# ON BOTH ROWS. The values below are the branch underneath's, as CI measured
# them, carried forward while this host cannot compare.
#
# Measured here against kanso#1516's head: interp_allocs 4,985,431 ->
# 4,810,435, a FALL of 174,996 (-3.51%), and interp_peak_bytes 942,308 ->

# allocations 5,310,694 -> 4,810,435 (-9.42%) and peak 933,280 -> 951,537
# (+1.96%).
#
# THE ALLOCATION FALL IS NOT THE MEMORY, and that is worth saying because the
# memory is what the change is about. `dispatch_loop_inner` cloned the whole
# overload VECTOR on every tail hop -- `self.fns.get(&*next).expect(..).clone()`
# -- and the groups are `Rc<Vec<..>>` now because the memory needs to hold one
# without borrowing from `self`. A tail hop takes a refcount bump instead. The
# 174,996 is that, and the memory's own rows are the rise beside it.
#
# The thunk counters are byte-identical across both changes.
#
# 2026-09-18, kanso#1517 on the tree merged with kanso#1516, CI's sitting.
# interp_allocs 4,985,433 -> 4,810,437, a FALL of 174,996 (-3.5101%) --

# 2026-09-18, kanso#1518 against main at kanso#1517, CI's sitting.
# 4,810,437 -> 3,879,653, a FALL of
# 930,784 (-19.3493%).
# EXACTLY what this container read. Not close: the same integer. An
# allocation counter counts operations rather than a host, so it travels
# where an instruction counter only nearly does -- the same law the two
# hosts showed at -325,263 and -174,996 on kanso#1516 and kanso#1517.
#
# 2026-09-18, kanso#1520 against main at kanso#1519, CI's sitting.
# 3,879,653 -> 3,843,587, a FALL of 36,066 (-0.9296%).
# -36,066, and this container read the same delta to the unit.
# 2026-09-18, kanso#1522: 3,843,587 -> 2,539,998, a FALL of 1,303,589
# (-33.92%), and it is the largest single move this vein has recorded. A
# binding allocated its name twice and now usually allocates it not at all:
# `match_one` pushed `name.as_str().to_owned()` into a `Bindings` and `bind`
# did `name.to_string()` on top of that. Storing a `Name` keeps twenty-two
# bytes or fewer in the node, and 99.77% of identifiers across lib/ are that
# short. The peak falls 67 bytes with it, which is the tail of the same thing:
# a node that holds its name inline frees nothing when it dies.
