# What an interpreted run holds, and the traffic it makes holding it.
#
# `KANSO_COUNTERS=1 kanso run interp_corpus --interp`, read off the same
# counting allocator the compiler's own row reads. The interpreted engine is a
# deployment rather than a stage of one: the program is parsed, inferred and
# then executed in this process, and nothing is emitted. So these rows cover
# the front end and the interpreter together. The compile veins cannot see
# either number, because they run `kanso check`, which stops before anything
# is executed.
#
# Two dimensions. interp_allocs is traffic, what the run asked the allocator
# for and gave back; interp_peak_bytes is residency, the most it held at once.
# A value allocated and dropped inside one step moves the first and not the
# second, and one change can move them opposite ways, so read the trade rather
# than either row alone. interp_peak_bytes is the interpreter-memory term of
# the welfare objective.
#
# Both belong to the rustc that built the compiler, as compile_peak_bytes
# does: a HashMap's growth schedule and a Vec's doubling are the standard
# library's, and the interpreter is Rust. The rows are exact for the host
# named on the measured-on line, and any other host refuses to compare. Across
# hosts, interp_allocs has read the same to the unit on two trees, because it
# counts what the program asked for; interp_peak_bytes has read eight bytes
# apart, because a high-water mark depends on what the allocator was holding
# at one instant. Take both rows from CI.
#
# A rise is a regression to explain and a fall is a win to bank: say which in
# design/compiler-log.md, which holds the history of every move.
# measured-on glibc=2.39-0ubuntu8.9 rustc=1.98.1
interp_allocs=624771
interp_peak_bytes=1298495
