# Retired instructions per benchmark, counted under callgrind. This is the
# work a process does, the dimension every other vein here is blind to:
# allocation counters say how often the allocator was called, the emitted
# golden how many lines the compiler wrote, the text golden how big the
# machine code is. None of them counts an instruction, and the decoder once
# slowed by eight and a half per cent with every allocation counter
# byte-identical. runbench's row is the run-speed term of the welfare
# objective.
#
# Exact, not a band. Three consecutive runs give the same digits, because
# callgrind counts rather than samples. A rise is a regression to explain and
# a fall is a win to bank: say which in design/compiler-log.md, which holds
# the history of every move.
#
# Measured with an empty environment (env -i). The kernel copies the
# environment block onto the new process's stack and libc walks it before
# main, so a run id that gained a digit would read as work nobody wrote.
#
# The rows belong to the linux runner's toolchain more tightly than any other
# vein here, because instruction count is what an optimiser's inlining moves
# most. Two glibc revisions of the same release differ by more than most
# changes this vein exists to catch, and the emitter probes clang for the
# preserve_none convention and writes a different module without it, so a
# clang-18 host cannot regenerate these rows. A toolchain bump looks like an
# enormous regression and is not one: regenerate every row in one go and say
# so in the log. The gate reads the two lines below and refuses any host they
# do not name.
