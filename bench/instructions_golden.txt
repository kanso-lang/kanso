# Retired instructions per benchmark, counted under callgrind. This is the
# work a process does, and it is the dimension every other vein here is blind
# to: allocation counters say how often the allocator was called, the emitted
# golden says how many lines the compiler wrote, the text golden says how big
# the machine code is. None of them counts an instruction.
#
# It exists because between 2026-07-27 and 2026-08-07 the decoder went
# 2,545,249,871 instructions to 2,762,364,162 — eight and a half per cent,
# matching the wall-clock regression almost exactly — with every allocation
# counter byte-identical the whole way. The chart called two of its lines
# "run speed" and "compile speed" and neither counted an instruction, so
# nothing anywhere could see it.
#
# Exact, not a band. Three consecutive runs give the same digits, because
# callgrind counts rather than samples and no other process can reach it. A
# rise is a regression to explain and a fall is a win to bank.
#
# Measured with an empty environment (env -i). The kernel copies the
# environment block onto the new process's stack and libc walks it before
# main, so a run id that gained a digit reads as fourteen instructions of work
# nobody wrote. With it pinned, two runs of unchanged code agree to the digit.
#
# These rows belong to the linux runner's compiler, and they belong to it more
# tightly than any other vein here: the same sources measured under Debian's
# clang read 2,762,364,313 for the decoder against ubuntu's 3,266,971,711,
# eighteen per cent apart, where the machine-code size of the same two builds
# differs by well under one. Instruction count is what an optimiser's inlining
# choices move most. So a toolchain bump will look like an enormous regression
# here and will not be one — regenerate every row in one go and say so in
# design/compiler-log.md, and never read a row against a number measured
# somewhere else.
#
# The line below is that rule, made checkable. The gate reads it, compares it
# against the host it is running on, and refuses to measure anywhere else —
# because the warning above did not stop this vein being regenerated from a
# container one glibc revision off the runner, whose rows sat about four
# hundred instructions low. Two ubuntu 24.04 boxes at 2.39-0ubuntu8.7 and
# 2.39-0ubuntu8.8 differ by more than most changes this vein is here to catch.
# measured-on glibc=2.39-0ubuntu8.8
#
# 2026-08-12 (later): basket 56,597,311 to 56,597,316, the other three unmoved.
# Five instructions, and they are the compare that stops `k_b_str_builder`
# re-seeding a header with room to spare. That guard takes an accumulator handed
# through one intermediate function from 752,908,406 instructions to 16,519,843
# at eight thousand appends. Five here.
#
# 2026-08-12 (later still): basket 56,597,316 back to 56,597,311, the same five.
# The guard is withdrawn — spare capacity is not sole ownership, and a builder
# that trusts it writes into a buffer somebody else holds, which took two
# rewritten panels of a book chapter to 88 GB. The 752,908,406 figure above is
# withdrawn with it rather than disproven: nothing re-measured it against the
# shape that matters.
# 2026-08-13: basket 56,597,311 to 55,987,313, a fall of 609,998 and 1.08%.
#
# 
# 2026-09-04 (a stack slot stands in the entry block): ten rows fall and two
# rise. The emitter wrote each call's argument array in the block that filled
# it; sixty-eight of the decoder's seventy-three slots stood outside their
# function's first block, which LLVM reads as a dynamic stack object — frame
# pointer kept, rsp restored through it on every return. jsonbench
# 2,098,864,471 -> 1,914,624,416, a fall of 8.778%. deepbench (+0.314%) and
# scanbench (+0.133%) rise, and they are the two whose .text grows most: a
# fixed frame gives LLVM a different layout to schedule against and it inlines
# differently in both directions. No allocation counter moves.
#
# 2026-09-05 (three arms at the utf-8 door): five rows fall and none rises.
# The counter and the ascii word-test came out from behind the wide SIMD pass
# into an always_inline front door, and a short run that is not ascii walks the
# grammar rather than paying the pass's seven constant loads. jsonbench
# 1,914,624,416 -> 1,877,751,716, a fall of 1.926%. oneshot -0.816%, widebench
# -0.301%, basket -0.050%, encodebench -0.004%. The other seven are
# byte-identical: they never reach utf-8 validation. No allocation counter
# moves and the emitted line count is unchanged — this is entirely inside the
# runtime.
#
# 2026-09-05 (two doors take registers instead of boxes, and k_str_n inlines):
# nine rows fall, three rise. work_jsonbench 1,877,751,716 -> 1,791,154,445, a
# fall of 4.612%: the find2 and slice prelude twins test the argument tags in
# the emitted module and hand a raw door scalars, so the boxed guards and the
# stack-passed fourth KValue go. work_indexbench 5,242,116 -> 4,792,124
# (-8.584%) and work_scanbench 1,425,334,005 -> 1,406,298,324 (-1.335%) are
# mostly k_str_n's always_inline; scanbench's NET fall is what matters, since
# the slice twin cost it 2,495,505 on its own and k_str_n returned more than
# that. work_oneshot 29,275,729 (-1.968%), work_widebench 57,839,394 (-0.741%),
# work_pendbench 700,501,795 (-0.230%), work_basket 39,875,796 (-0.096%),
# work_encodebench 5,802,859,663 (-0.085%), work_digestbench 80,995,637 (-781).
#
# THREE RISE. work_deepbench 678,049,713 -> 678,049,725 and work_escapebench
# 130,170,743 -> 130,170,757 are twelve and fourteen instructions, which is the
# twins' tag tests on the few calls those programs make. work_readbench
# 2,000,657,813 -> 2,038,393,968, a rise of 1.886%, is k_str_n and is real: that
# benchmark reads a file and holds few short strings and many long ones, and an
# inlined copy loop loses to a called one when the copy dominates. The objective
# takes the trade -- see the entry of the same date, and bench/text_golden.txt
# for the 34,320 bytes of machine code it also costs.
#
# 2026-09-05 (third): the utf8-over-slice twin. Three rows fall and nine hold
# EXACTLY still, which is what the local A/B predicted: eight of the twelve
# benchmark binaries came out byte-identical to the ones before the change, so
# those rows could not move, and widebench's binary differed while its count
# did not. work_jsonbench lands on 1,783,183,295, a fall of 7,971,150 and
# 0.4450%. work_oneshot lands on 29,222,587, a fall of 53,142 and 0.1815%.
# work_encodebench lands on 5,802,806,121, a fall of 53,542. The container
# measured the same three deltas TO THE INSTRUCTION on its own pair of builds,
# which is the strongest agreement this vein has recorded between the two
# hosts.
#
# 2026-09-05 (fourth): the find2_below twin. TWO rows fall and TEN hold exactly
# still. work_encodebench lands on 5,563,212,521, a fall of 239,593,600 and
# 4.1289%. work_oneshot lands on 28,623,603, a fall of 598,984 and 2.0498%.
# Nothing rises. The container's local A/B measured both deltas TO THE
