# What an INTERPRETED run costs, counted rather than timed.
#
# `kanso run --interp` on bench/interp_corpus, anchored at
# `run_interpreted_on_stack` -- the entry of the thread the interpreter runs
# on. `kanso::main` is the wrong anchor here and the first sitting says why:
# it read 48,026,664 against 2,700,128,254 for the whole process, because
# `kanso run --interp` pins a one-gigabyte stack and hands the program to a
# thread of its own, so the main thread holds the front end and 1.8% of the
# run.
#
# THE CORPUS BUILDS ITS OWN INPUT. It interpolates a document of 220 objects
# and decodes it six times, so the workload is a property of the corpus alone.
# Every other benchmark in this tree reads bench/large.json, and a row that
# reads a file is a row that moves when the file does.
#
# WHY IT EXISTS. Clay ruled on 2026-09-16 that the objective becomes a
# development welfare, a production welfare and a meta over them, and named the
# interpreted engine's own order: "start-time is vastly more important than
# speed which is more important than memory usage." This is the middle of the
# three. It is an exact vein of its own and not yet an objective term, the way
# `.text` is under the 2026-09-05 ruling.
#
# 2026-09-16 (the vein opens, and it opened onto a reproduction failure):
# two runs of one binary over one corpus read 2,651,460,189 and 2,648,375,305,
# 3,084,884 apart, where the front end's own anchor read 48,026,664 twice. The
# interpreter's tables -- `fns`, `types`, `knots`, the typeset cache and the
# two cycle-guard sets -- were `std::collections`, whose `RandomState` draws a
# fresh key from the OS on every process, so each run probed them in a
# different order and did a different amount of work reaching the same answer.
# That is exactly the defect kanso#1449 cost three CI rounds to find on the
# compile path, still living in the one file the spec that catches it excused.
# The excuse was "the interpreter's own cost is not counted by any exact
# vein", and this file is that vein, so it is gone and src/eval.rs is spelled
# `crate::hash` now.
#
# It is a fall as well as a fix: three consecutive runs read 2,375,580,224,
# which is 275,879,965 below the first of the two disagreeing readings, a
# 10.40% fall. SipHash-1-3 was hashing the interpreter's every name lookup.
#
# The row below is THIS CONTAINER's, rustc 1.94.1 against the runner's 1.98.1,
# so the gate refuses to compare it here. Round one is deliberately red and
# CI's own reading is what stands.
# 2026-09-16 (CI's own first sitting): the row above was this container's
# 2,375,580,224 and the runner reads 2,324,888,431, 2.18% lower. The container
# reads about 1.2% HIGH on the three compile rows, so this row's divergence is
# the same sign and about twice the size -- an interpreted run is mostly the
# interpreter's own loop, where a compile is mostly the front end's, and the
# two do not have to move together between toolchains. CI's is the number.
#
# 2026-09-17, kanso#1462, round four. The interpreted run falls 3,920,499
# on the head merged with kanso#1464: the linearity analysis runs on the
# interpreter's compile path too, and indexing it is felt here. CI read
# 2,320,967,932 and then 2,320,967,932 again in the same job -- the six
# instructions this row used to move by were the allocator picking a
# random base address, which kanso#1466 took away.
