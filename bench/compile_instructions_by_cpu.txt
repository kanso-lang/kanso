# What `kanso check lib/json` retires, ONE ROW PER CHIP.
#
# bench/compile_instructions_golden.txt holds the same quantity as a single
# number, and that single number is a fiction the runner pool does not
# support. The pool is at least four CPUs — an AMD EPYC Zen 3 (family 0x19
# model 0x1), an Intel Ice Lake-SP (0x6/0x6a), the Cascade Lake this was
# written on (0x6/0x55), and whatever else Azure has that week — and glibc
# resolves memcpy, memcmp and strlen by ifunc at load time. One libc runs
# different code on different silicon, and the compiler runs that code.
#
# HOW BIG THE EFFECT IS, MEASURED. A pull request that changed
# docs/compiler.html and design/compiler-log.md and nothing else read
# 41,500,177 against a golden of 41,495,096: 5,081 instructions from an
# edit the compiler cannot see. Four earlier readings on this vein — +6,087,
# -416, +8,032, -3,289 — were written up as layout effects, and two of them
# are smaller than that 5,081. Nothing in them separated the change from the
# chip, so the change could not be read off the row at all.
#
# AND THE ROW STILL CARRIES REAL SIGNAL, WHICH IS WHY THE FIX IS NOT A
# TOLERANCE. Held on one chip, with the binary's sha printed on both reads,
# the beat-rewind split in kanso#1226 moves this row -5,621: reproducible,
# exact on repeat, and the same size as the chip effect it was being confused
# with. A band wide enough to swallow the noise swallows the signal too. So
# the noise gets a key instead.
#
# WHAT A KEY IS. scripts/gates/dispatch.sh `key` prints family and model and
# nothing else — no cache sizes, no derived thresholds, nothing a firmware
# revision could move under a row that is otherwise right. A host with no x86
# loader reports `unnamed` and is pinned under that name like any other.
#
# HOW THIS FAILS. An unrecorded chip does not pass and does not warn: it goes
# red asking for a sitting, and prints the line to add. A recorded chip whose
# row moved goes red the way it always did. There is no answer that lets an
# unknown number through, which was the whole objection to recording one
# block and skipping when it differs — three runs in four land on a cpu that
# is not the recorded one, so most regressions would have been waved through
# and the ratchet's mutations would have gone blind on those runs.
#
# WHAT IT COSTS. A change that moves the front end invalidates every chip's
# row at once, and only CI can re-sit them, one chip per run. So such a change
# takes several pushes to re-pin, each one red with a paste-ready line. That
# is the price of a row that means something; the alternative priced at zero
# is a row that reads the runner.
#
# THE FIRST ROW IS THE REFERENCE, and its value is the one
# bench/compile_instructions_golden.txt carries as a bare
# `compile_instructions`, because welfare, the trend gate and golden_prose all
# read that file for a single number and a per-chip series is only comparable
# to itself. The gate checks the two agree on every run, on any chip, so the
# golden cannot drift from the table it summarises. Which chip is first is
# arbitrary and means nothing beyond "this is the series welfare tracks".
#
# measured-on glibc=2.39-0ubuntu8.8 rustc=1.98.1
#
# 2026-09-03: the runner's rustc moved 1.98.0 -> 1.98.1 and this line moves
# with it. THE POINT RELEASE MOVED NOTHING. CI re-sat all three compile veins
# under 1.98.1 on family0x6-model0xcf, binary sha de5bfab22fbd, and every
# number came back identical to the one recorded under 1.98.0:
# compile_allocs 25,485, compile_peak_bytes 715,275, compile_instructions
# 41,831,767. Only the measured-on line changes.
#
# That is one datum against the granularity this file pins. measured_on.sh's
# own header says of rustc: "the upstream version only ... nothing here shows
# a point release moving a count, and pinning tighter than the evidence reds
# the gate on changes that are not changes." A patch bump reddening three
# gates while moving no number is exactly that shape. It is ONE observation
# and the pin is not loosened on it; the next point release is the second.
#
# WHY TWO ROWS LEFT ON 2026-09-03. src/main.rs embeds the runtime with
# `include_str!("runtime.c")`, so a change to the runtime changes the compiler
# binary even when it changes no compiler code: this branch left .text, .data
# and .bss byte-identical at 2,513,746 / 2,648 / 304 and still moved the Zen 4
# row 41,495,850 -> 41,498,829, because the embedded source grew and the
# rodata after it shifted. The front end does the same work at different
# addresses.
#
# That invalidates every chip at once, and a value measured against the old
# binary is worse than no value, so the Intel and Zen 3 rows were removed
# rather than carried forward. They are not new chips when they next refuse —
# they are re-sittings, and the number to paste comes from that run's log the
# same way.
#
# THE FAMILY-AND-MODEL KEY IS NOT OVER-KEYING, and the evidence arrived by
# falsifying the opposite claim. On the binary before this one, Zen 3
# (0x19/0x1) and Zen 4 (0x19/0x11) agreed to the instruction at 41,495,850,
# against the Intel's (0x6/0xcf) 41,500,974 — which read as the key being finer
# than the effect, since glibc's ifunc resolver picks memcpy and memcmp by
# feature set rather than by model. On this binary the same two models read
# 41,503,893 and 41,498,829: they differ by 5,064.
#
# So the agreement was a property of that binary's layout, not of the silicon,
# and a key coarse enough to merge the two AMDs would have carried one model's
# number for the other from this commit onward. Two models sharing a value once
# is not evidence they share a value.
#
# Two things move this row and only one of them is the chip. The other is the
# binary, and a row is only ever comparable within one of those.
#
# Rows are `<dispatch.sh key> <retired instructions>`. CI's toolchain owns
# these values and CI is the only thing that may write them, one chip per run,
# out of the job log.

# EVERY ROW WAS CLEARED ON 2026-09-03, and what refills them is a different
# measurement. Emptying the environment left this row in two stable clusters
# 5,064 apart and the SAME family and model produced both, so the key this file
# is named for was never sufficient. compile_instructions.sh now pins the glibc
# tunables; the comment there carries the profile evidence.
#
# WHAT THE NEXT RUNS TEST. If pinning worked, every chip lands on ONE value and
# the per-chip key is vestigial — at which point this file collapses back to a
# single golden and the ratchet row goes with it. If the chips still disagree,
# pinning was the wrong explanation and the tunables come out again. Either
# answer is worth the runs; a row nobody can compare measures nothing.
#
# RE-SAT ON 2026-09-03 for the wrong-arity reorder. src/main.rs embeds the
# runtime with `include_str!("runtime.c")`, so the k_call1..k_call4 change moved
# this row 41,631,006 -> 41,631,998 on the SAME family and model: +992, from the
# embedded source growing and the rodata after it shifting, not from front-end
# work. The paragraph above predicted exactly this and it is the second time
# this file has been emptied for it in one day.
#
# The Intel (0x6/0xcf) and Zen 4 (0x19/0x11) rows measured against the previous
# binary are removed rather than carried forward, for the reason already written
# above: a value measured against the old binary is worse than no value. They
# are re-sittings when they next refuse, not new chips.
# Zen 4 re-sat from the run at 51a671b2, which printed the paste-ready line
# itself. On THIS binary the two AMD models agree to the instruction, where on
# the previous one they read 41,503,893 and 41,498,829 — 5,064 apart. The
# paragraph above says two models sharing a value once is not evidence they
# share a value, and this is the same pair doing it a second time on a third
# binary. They stay keyed separately: the evidence is that they agree here, not
# that they agree.

# RE-SAT ON 2026-09-03: 41,631,998 -> 41,831,767 on the same family and model,
# +199,769, or 0.48%. This IS front-end work, and it belongs to the json
# library's extra arms rather than to the raw byte switch that shipped in the
# same branch. `kanso check` never runs the backend, so a codegen change can
# only reach this row through the binary's layout — the second cause named
# above.
#
# Decomposed on the container, three builds, same tunables:
#
#   main                                 42,032,508
#   the library change alone             42,238,115   +205,607
#   the library change and the switch    42,235,790     -2,325
#
# So the library is the whole of it and the switch gives 2,325 back, which is
# inside the layout band this file's header documents in thousands. The rise
# buys 17.14% of the decoder's runtime, which is the trade the objective
# weighs.
#
# The Zen 4 row is removed rather than carried forward, for the reason written
# above: it was measured against the previous binary and a value measured
# against the old binary is worse than no value. It is a re-sitting when it next
# refuses, not a new chip. The binary this row belongs to is sha 55fb850296d1.

# 2026-09-03, THE THIRD CAUSE, and it is the one this file said it could not
# rule out. compile_instructions.sh prints a `compile_sample cpu= sha= row=`
# line on every run precisely so that "same cpu and same sha with different
# rows would mean something is moving that neither the key nor the diff can
# see". That is what happened.
#
# family0x6-model0xcf, binary sha 55fb850296d1, two runs:
#
#   12:33  41,832,275   (the sitting that first recorded this chip)
#   13:05  41,831,767   (a branch whose whole diff is two markdown files)
#
# 508 apart, same key, same binary. So the key does not determine the row, and
# the premise this file rests on is weaker than it claimed. Nothing in the
# second branch can reach the front end — design/compiler-log.md and its
# archive, nothing else — so a front-end change is ruled out by the diff.
#
# The row moves to 41,831,767 because three readings now say it (Zen 3, Zen 4,
# and this chip at 13:05) against one that says 41,832,275, and because a row
# CI disagrees with two times in three is worse than one that is merely not
# yet explained. That is a choice under uncertainty and not a measurement:
# the honest state is TWO readings of one key on one binary, differing.
#
# OPEN, and it wants a sitting rather than a guess: run the box several times
# on one Emerald Rapids runner and see whether the value is bimodal there the
# way it was across the two AMD models before the tunables were pinned. If it
# is, the missing term is something the pinned tunables do not cover, and the
# candidates are the ones the header already names as excluded from the key —
# cache sizes and derived thresholds — reaching the row by a path other than
# the malloc and string tunables this gate sets.
#
# The row itself is edited in place above rather than appended here, because
# the reader takes the FIRST row matching a key and stops. A second
# family0x6-model0xcf line at the bottom of this file would be read by nobody
# and would look authoritative to everybody, which is how a golden goes quiet.
#
# 2026-09-03, the rustc bump and the two rows nobody re-sat. CI landed on
# family0x6-model0xcf under 1.98.1 and read 41,831,767, the same number 1.98.0
# read. The Zen 3 and Zen 4 rows above were measured under 1.98.0 and are
# CARRIED ACROSS rather than removed.
#
# That is an assumption and it is stated rather than hidden: the toolchain
# changes the binary identically for every chip, and the one chip that was
# re-sat moved by nothing, so the other two are expected to hold. kanso#1230
# removed a row rather than carry one across a toolchain move, and the
# difference is that this time there IS a measurement — deleting two correct
# values to force sittings that would reproduce them buys nothing.
#
# The assumption is self-correcting and costs nothing to be wrong about: a
# carried row that is wrong goes red the first time CI lands on that chip,
# which is the same signal a missing row would have given, one run later.
#
# 2026-09-03, LATER, and the guess above is WRONG. Both runs printed their
# full 123-line cpu feature block, because no bench/dispatch.txt is recorded
# and `dispatch.sh name` dumps the block in CI while none is. The two blocks
# are byte-identical — every feature word, the stepping, and
# data_cache_size among them — so cache sizes and derived thresholds are
# ruled out, and they were the candidates the note above proposed.
#
# What moved is visible in the profiles the same two job logs carry, and it
# is not the compiler. Every kanso symbol agrees to the instruction across
# the pair — eval_expr'2 1,633,593 both times, check_merged 1,589,240,
# lex_line 866,486, parse 589,004, all of them. Three rows differ and all
# three are glibc:
#
#   _int_malloc           1,551,384 -> 1,551,964   +580
#   _int_free             1,522,333 -> 1,522,352    +19
#   memcmp-avx2-movbe     1,353,408 -> 1,353,342    -66
#
# So the front end executed the identical instruction sequence and the
# allocator did not. That is the same shape this file's header records for
# the 5,064 cluster the tunables were pinned to remove: _int_malloc and
# memcmp moving together, which is an alignment difference downstream of a
# heap-layout difference. Pinning the tunables shrank it from 5,064 to 508.
# It did not remove it.
#
# The thread stays OPEN and its question is narrower now: what still moves
# the heap layout when the binary, the cpu features, glibc, valgrind and the
# environment all agree? Not "is it the cpu" — that is answered, and the
# answer is no.
