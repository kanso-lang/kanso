# Widening the gate found these. The scan it replaced stopped a message at the
# first comma a lowercase word followed, which for a message that holds such a
# comma left the quote unclosed and the call site invisible — twenty-four of
# them. Twelve now have goldens or a test. The two below are different: no
# program can reach either, and the mechanism is named here so nobody spends
# another sitting writing programs for them. Neither is deleted, because both
# arms are the safe side of a fork — see task #69.
#
# The other four were each said to be answered first by a check added later.
# An inline constant never reaches the parser carrying a block: the lexer folds
# an indented line into its head unless that head opens one, and a `>>` or `.`
# continuation is legal, so the shape does not exist. A non-identifier in a
# constant's name position is refused first by "a top-level line must begin
# with `fn`, `type`, or a constant binding". The private-type message fired on
# a leading underscore, which the naming rule retired — and the check behind it
# was deleted once that was checked by running a program rather than by reading
# the source, so the line is gone from here too.
#
# That is the pattern worth naming: a diagnostic can be shadowed by a better
# one added later, and nobody notices, because it simply stops appearing.
#
# The reading it is not safe to do is the one that says which check speaks
# first. Two of the excuses written here were wrong. The inline-constant claim
# missed heads that OPEN blocks and left on 2026-08-20. The claim that an
# indented top-level line is always taken by the indentation rule or the
# blank-line rule held only where a declaration precedes it: put the indented
# line first in the file and there is nothing above it for either rule to work
# against, so the top-level loop refuses it and says so. That one is pinned at
# an_indented_first_line and has left this list too. An excuse is worth what
# the program written to test it is worth.
#
# The indented-block rule cannot fire because the lexer decides, before the
# parser sees anything, which indented lines stay lines. `is_block_header`
# keeps a deeper line only under `if`, `x = if`, `else`, `build` or
# `x = build`; under anything else the line is folded into its head as one
# more argument. So `parse_block_construct` is only ever handed a head it
# already accepts, and `else` is taken by its callers first.
#
# The unused-expression rule left this list on 2026-08-27, and its excuse is
# the third here to be shown wrong by a program. The reasoning above it —
# `reject_never_effect` refuses a non-final literal, list, map, lambda or
# binary operation, and consecutive expression statements fold into one `Seq`
# — is true of the walk over a function body, and there are TWO walks. The one
# that handles `build` and block bodies had no such check, so an effect line in
# a build was neither run nor complained about: three `io/write` lines ran the
# last and lost the other two, in silence, on both engines. The check is in
# that walker now and the case is pinned at
# tests/golden/errors/a_build_body_line_goes_nowhere.
#
# The lesson is the one the top of this file already states, sharpened: an
# excuse that reasons about which check speaks first has to name WHICH walk it
# is reasoning about, because a second one may not have the rule at all.

# THE PRINTED FAMILY. `error[kind]: …` written as plain text is what a rendered
# Diagnostic looks like on a terminal, so these read to a user exactly like a
# message the corpus pins. The scan learned this third opener after the second;
# ten sites, and one of them is excused.

# ONE IS UNREACHABLE ON UNIX, and this is a claim about control flow rather
# than a reading of what looks unlikely. src/main.rs calls `ended_by_signal`
# only from the `None` arm of `code.code()`. On unix, `ExitStatus::code()`
# answers None exactly when a signal ended the process, and in exactly that
# case `ExitStatusExt::signal()` answers Some — so the `None` arm INSIDE
# `ended_by_signal` cannot be reached. It stays because the match on an Option
# must be exhaustive. The `#[cfg(not(unix))]` body returns the same sentence
# unconditionally and is reachable on Windows, which CI does not run.
