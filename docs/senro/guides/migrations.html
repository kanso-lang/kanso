migrations

a migration is a change to the database's tables, kept in the app so that every copy of the database is built the same way. senro keeps each in a file of its own, as Rails keeps them in db/migrate, and the file's name says when it was written. this guide covers the files, the order they run in, how a run is recorded, and the generator that writes them. the models guide covers what the app does with the schema they build.

a file to a migration

an app's migrations live in its migrations directory. the guestbook has seven.

shell
$ ls examples/guestbook/migrations
20261030014602_create_signatures.kso
20261104045753_create_accounts.kso
20261105044946_add_email_to_accounts.kso
20261105050729_add_confirmed_to_accounts.kso
20261105065821_add_lock_to_accounts.kso
20261105070000_add_sign_ins_to_accounts.kso
20261105100325_add_photo_to_signatures.kso

a file is named <stamp>_<name>.kso. the stamp is the moment the file was written, as fourteen digits: the year, month, day, hour, minute and second, in UTC. the name says what the migration does. the file holds one pub constant with that name, and its value is the change.

examples/guestbook/migrations/20261030014602_create_signatures.kso
import "../../../models"

pub create_signatures = models/create_table "signatures" [
  (models/column "name" "text")
  (models/column "message" "text")
]

a migration that makes several changes holds a list of them. this one adds five columns to accounts. the directory is one kanso module, so its files share their names, and a name a file keeps for itself, such as sign_in_count here, is spelled so that no other migration uses it.

examples/guestbook/migrations/20261105070000_add_sign_ins_to_accounts.kso
import "../../../models"

# How many times the account has signed in, and when and from where the
# latest sign-in and the one before it came, as Devise's trackable keeps them.
pub add_sign_ins_to_accounts = [
  (models/add_column "accounts" sign_in_count)
  (models/add_column "accounts" (models/column "current_sign_in_at" blank_text))
  (models/add_column "accounts" (models/column "last_sign_in_at" blank_text))
  (models/add_column "accounts" (models/column "current_sign_in_ip" blank_text))
  (models/add_column "accounts" (models/column "last_sign_in_ip" blank_text))
]

sign_in_count = models/column "sign_in_count" "integer not null default 0"

blank_text = "text not null default ''"

the changes

a change is a call of senro's models module. there are six.

  • models/create_table name columns makes a table. a column is models/column name kind, where the kind is what Postgres is told, such as "text" or "integer not null default 0". models/created_at and models/updated_at are the two columns Rails' t.timestamps adds.
  • models/add_column table column adds a column to a table that is there.
  • models/rename_column table from to renames one.
  • models/drop_column table name removes one.
  • models/add_foreign_key table column parent makes the column hold a row of parent, and removes the row when its parent is removed.
  • models/add_unique_index table column lets a value appear once in the column.

each does nothing when its work is already done: a table is made if it is not there, a column added if the table lacks it. a database that was built before its migrations were recorded takes them all safely the first time.

the notebook's pages belong to a note, so the migration that makes their table also adds the foreign key. the one that makes its users lets an address appear once:

examples/notebook/migrations/20261111180513_create_pages.kso
import "../../../models"

pub create_pages = [
  pages_table
  (models/add_foreign_key "pages" "note_id" "notes")
]

pages_table = models/create_table "pages" [
  (models/column "body" "text")
  (models/column "note_id" "integer not null")
]
examples/notebook/migrations/20261111180514_create_users.kso
pub create_users = [users_table (models/add_unique_index "users" "email")]

a change is a value, so a migration can name its changes and list them, as these do with pages_table and users_table.

the order they run in

migrations run in the order of their files' names, and the stamp at the front of each name makes that the order they were written in. the order does not depend on the machine, on what the constants are called, or on the order the compiler reads the files in. two people who build a database from the same files get the same tables.

the app's entry does not list the files. derive app/conventions reads them from the module: each stamp, beside what its file holds, oldest first. the same derivation folds the migrations, in the same order, into the schema the app is compiled against. so there is no schema file to keep in step, and a migration that renames a column the app still reads is a compile error at the read until the app is changed with it.

a file whose name is not its stamp and its constant's name has no place in that order, and the app does not compile.

spec/errors/migration_misnamed/migrations/create_notes.kso
import "../../../../models"

pub create_notes = models/create_table "notes" [(models/column "title" "text")]
kanso check .
error[derive]: migrations/create_notes.kso holds `create_notes`, so it is named <yyyymmddhhmmss>_create_notes.kso
  --> ./migrations/create_notes.kso:3:5
   3 | pub create_notes = models/create_table "notes" [
           ^

a second file with a stamp another has is refused the same way, since a stamp is what one migration is recorded under.

running them

app/run runs them as the app starts, so a server never answers a request against tables older than its code. senro migrate runs the same thing and stops, for a deploy that migrates before it restarts.

shell
$ senro migrate
migrated

each migration runs in a transaction of its own and is recorded in a senro_migrations table when it has run: the app's name, the migration's stamp, and the SQL it ran. a later start runs only the ones the table does not list. because they are found by stamp, a migration that arrives late, from a branch merged after newer ones were written, is still run.

a migration that has run is history. if its file is edited afterwards, the SQL it would run no longer matches what was recorded, and the app refuses to start and says which one. a new change is a new migration.

a start after a migration was edited
notebook's migration 2 has changed since it ran:
  ran: alter table notes add column if not exists body text
  now: alter table notes add column if not exists body varchar(80)

that message is from an app that keeps its migrations in one file, where each is known by its place in the list. an app with a file to a migration is told the stamp.

writing one

senro generate migration writes a migration's file, stamped with now. it reads what to write from the name, as Rails' generator does.

shell
$ senro generate migration create_labels name:text
  create ./migrations/20261111180513_create_labels.kso
$ senro generate migration add_color_to_tags color:text post:references
  create ./migrations/20261111180514_add_color_to_tags.kso
$ senro generate migration rename_color_to_shade_in_tags
  create ./migrations/20261111180515_rename_color_to_shade_in_tags.kso
$ senro generate migration remove_shade_from_tags shade
  create ./migrations/20261111180516_remove_shade_from_tags.kso

create_<table> makes a table with an id, a column for each field and the timestamps. add_<something>_to_<table> adds a column for each field, with a foreign key for a references field and a unique index for one marked :uniq. remove_<something>_from_<table> drops each column named. rename_<old>_to_<new>_in_<table> renames one.

the file the second command wrote
import "<senro>/models"

pub add_color_to_tags = [
  (models/add_column "tags" (models/column "color" "text"))
  (models/add_column "tags" (models/column "post_id" "integer not null"))
  (models/add_foreign_key "tags" "post_id" "posts")
]

any other name makes a migration with no changes in it and a comment listing the six calls, for the app to fill in. a field is written as scaffold reads it, name:text, name:int, name:references or name:attachment. a migration's name is lowercase words joined by underscores, at most 48 characters. two migrations written in the same second take that second and the next, so they keep the order they were written in.

one file, for a small app

a module that is a single file, migrations.kso, and writes pub all = [...] itself is read as it is, and each change is recorded by its place in the list. senro's own specs use this for apps of a few lines. the generators write files, and leave an app that keeps one file alone.

spec/db/associated/migrations.kso
import "../../../models"

pub all = [
  writers
  notes
  pages
  covers
  pages_to_notes
  notes_to_writers
  covers_to_notes
  one_cover
]

writers = models/create_table "writers" [name]

notes = models/create_table "notes" [title author_id]

pages = models/create_table "pages" [note_id body]

covers = models/create_table "covers" [note_id image]

pages_to_notes = models/add_foreign_key "pages" "note_id" "notes"

notes_to_writers = models/add_foreign_key "notes" "author_id" "writers"

covers_to_notes = models/add_foreign_key "covers" "note_id" "notes"

one_cover = models/add_unique_index "covers" "note_id"

name = models/column "name" "text not null"

title = models/column "title" "text not null"

author_id = models/column "author_id" "integer not null"

note_id = models/column "note_id" "integer not null"

body = models/column "body" "text not null"

image = models/column "image" "text not null"

what is not here

there is no command to roll a migration back. a migration is a list of changes and nothing records how to undo one: renaming a column back is clear, and what a dropped column held is gone. the way to undo a change today is to write the migration that reverses it.
