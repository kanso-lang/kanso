senro guides

routing

a senro app has no routes file. each public function in one of its modules is an action, and the module's name and the function's name place it. this guide starts with a whole app's routes, then covers the seven actions, what to do with an action that is not one of them, how an id reaches an action, singular resources, resources nested under another, naming a route from code, keeping an old URL working, and what senro's routing cannot express.

the routes file you will not find

a Rails app lists its routes in config/routes.rb, as nested calls to resources. a senro app has no such file. the notebook that the generators guide builds has notes, pages that belong to a note, readings served as JSON, and accounts. in Rails, its routes file would read like this:

config/routes.rb, as a Rails app would write it
Rails.application.routes.draw do
  root "home#index"

  resources :notes do
    resources :pages
  end
  resources :readings, except: [:new, :edit]

  resource :registration, only: [:new, :create]
  resource :session, only: [:new, :create, :destroy]
  resources :resets, only: [:new, :create, :edit, :update]
  resources :confirmations, only: [:edit, :update]
  resources :unlocks, only: [:edit, :update]
end

senro reads the same table from the app's modules. each module is a resource, named for its file, and each public function in it is an action, named for the function. the notebook's three resource modules declare these actions, bodies left out:

examples/notebook/notes.kso
pub fn index req db

pub fn show req db id:int

pub fn new req _

pub fn create req db

pub fn edit req db id:int

pub fn update req db id:int

examples/notebook/pages.kso
pub fn index req db note_id:int

pub fn show req db note_id:int id:int

pub fn new req db note_id:int

pub fn create req db note_id:int

pub fn edit req db note_id:int id:int

pub fn update req db note_id:int id:int

pub fn destroy _ db note_id:int id:int
examples/notebook/readings.kso
pub fn index req db

pub fn show _ db id:int

pub fn create req db

pub fn update req db id:int

pub fn destroy _ db id:int

each line does the work of a line in routes.rb. notes.kso defines all seven actions, so it is resources :notes. every action in pages.kso takes a note_id before its own id, so the pages nest under the notes, as resources :pages does inside the notes' block. readings.kso has no new and no edit, so it has no routes for them, as except: [:new, :edit] says in Rails. the modules the authentication generator writes, session.kso and the rest, place theirs the same way.

the seven actions

a resource is a module, and its actions are the seven Rails gives a resource. for a module named posts:

actionrequestwhat it is for
posts/indexGET /postsevery post
posts/newGET /posts/newa form for a new one
posts/createPOST /postsmake one from the form
posts/showGET /posts/:idone post
posts/editGET /posts/:id/edita form to change it
posts/updatePATCH /posts/:idchange it from the form
posts/destroyDELETE /posts/:idremove it

a module named home is the exception: home/index answers GET /. a browser's form can only send GET and POST, so a form that means PATCH or DELETE posts a hidden field, _method, and the server reads the request as that method. a public function with any other name is refused where it is declared, so a misspelled action never becomes a dead route.

actions beyond the seven

a Rails app reaches past the seven actions with a member route, post :publish, on: :member, or a collection route, get :search, on: :collection. senro has neither. a public function in a resource's module is one of the seven or it is refused:

kanso check, in spec/errors/misspelled_action
error[derive]: `destory` is not an action: name it index, new, create, show, edit, update or destroy
  --> ./posts.kso:4:8
   4 | pub fn destory _
              ^

the custom action becomes a resource of its own, the way DHH describes the controllers at 37signals. publishing a post makes its publication, and withdrawing it removes the publication. a post has one, so the module is singular, and its actions take the post's id, so it nests under posts:

spec/runs/actions_as_resources/publication.kso
# Publishing a post is making its publication, and withdrawing it is
# removing that, as Rails' `resource :publication` nested under posts has
# it. There is one publication to a post, so the actions take the post's id
# and no id of their own.
pub fn create _ _ post_id:int
  "post {post_id} published"

pub fn destroy _ _ post_id:int
  "post {post_id} withdrawn"

a search over the posts is a resource too, with an index that reads the query string:

spec/runs/actions_as_resources/searches.kso
import "../../../web"

# A search over the posts is a resource of its own: its index reads the
# query string.
pub fn index req _
  q = web/query req
  "posts matching {web/value q "q"}"

with a posts module that has index and show, the app's routes, and the paths path_to "publication/create" 3 and path_to "searches/index" name, are these:

kanso run, in spec/runs/actions_as_resources
["DELETE /posts/:post_id/publication" "GET /posts" "GET /posts/:id" "GET /searches" "POST /posts/:post_id/publication"]
/posts/3/publication
/searches

the same move covers the other actions people add to a controller. archiving is an archive resource nested under what it archives, a bulk edit is an edit on a resource named for the batch, and a dashboard is the index or show of a module named for it. each new module is a file with an obvious name, and its actions get the same checks as any other.

ids

an action whose route has :id takes it as a third argument. annotated as an int, it reaches the action as one, and a segment that is not a number is not that route.

spec/runs/singular/posts.kso
pub fn index _ _
  "every post"

pub fn show _ _ id:int
  "post {id}"

the annotation matters for more than conversion. GET /posts/new and GET /posts/:id would both answer /posts/new if id could be any word, and senro refuses the pair.

spec/errors/overlapping_routes/posts.kso
pub fn new _
  "a blank form"

pub fn show _ id
  "post {id}"
kanso check
error[derive]: `GET /posts/:id` and `GET /posts/new` (posts/new) answer the same request: annotate `id` as `int` so a word is not taken for an id
  --> ./posts.kso:4:8
   4 | pub fn show _ id
              ^

singular resources

some resources have one of them per visitor: a profile, a session, a cart. a module whose show, edit, update and destroy take no id is a singular resource, as Rails has them. its routes drop the :id, and it has no index.

spec/runs/singular/profile.kso
import "../../../routes"

pub fn show _ _
  "your profile is at {routes/path_to "profile/show"}"

pub fn edit _ _
  "edit it"

pub fn update _ _
  "saved"

with the posts module above, the app's routes are these:

the route table's keys
["GET /posts" "GET /posts/:id" "GET /profile" "GET /profile/edit" "PATCH /profile"]

the guestbook's sign-in is one: session/new is the form at GET /session/new, session/create signs in at POST /session, and session/destroy signs out at DELETE /session.

nested resources

a comment belongs to a post, and its URL can say so. a module whose actions each take the parent's id right after the request and the database is nested under the parent: comments/index req db post_id answers GET /posts/:post_id/comments, and comments/show req db post_id id answers GET /posts/:post_id/comments/:id. the parameter's name places the route, as the action's name does: post_id puts it under /posts. an annotation reads the same way as it does for id, so a post_id:int that is not a number is no route.

spec/serve/nested_routes/comments.kso
import "std/net/http"

# Each action takes the post's id, so the routes nest under it:
# `comments/index` answers GET /posts/:post_id/comments. Removing one needs a
# sign-in, so the server sends that request to sign in first.
pub without_sign_in = ["index" "create" "show"]

pub fn index _ _ post_id:int
  effect (http/text_page "the comments on post {post_id}")

pub fn create _ _ post_id:int
  effect (http/text_page "a comment made on post {post_id}")

pub fn show _ _ post_id:int id:int
  effect (http/text_page "comment {id} on post {post_id}")

pub fn destroy _ _ post_id:int id:int
  effect (http/text_page "comment {id} gone from post {post_id}")

the server hands the action the parent's id first and its own id second. every action of a nested module takes the parent's id in that place, and one that does not is refused where it is declared. nesting goes one level deep, which is what Rails' guides advise: a comment's URL needs its post and nothing above it, so a module nested under comments answers under /comments/:comment_id.

a nested route named from code takes the parent's id before its own: path_to "comments/show" 3 4 is /posts/3/comments/4, and a call that leaves the parent out is refused with the form it should take.

spec/runs/nested_routes/comments.kso
pub fn index _ _ post_id:int
  "the comments on post {post_id}"

pub fn show _ _ post_id:int id:int
  "comment {id} on post {post_id}"

naming a route

routes/path_to answers a route's path, so a link or a redirect never spells a path by hand. it takes the route's name, written whole as a string, and an id for each id the route has: the parent's first, then its own. there is one form, so a reader always sees which route a call names.

spec/runs/path_to/posts.kso
import "../../../routes"

pub fn index _
  "every post: {routes/path_to "posts/index"}"

pub fn show _ id:int
  "post {id} is at {routes/path_to "posts/show" id}"
kanso run
post 3 is at /posts/3
every post: /posts
/posts/7
/

the call is checked while the app compiles. a name that is no route is refused at the call, and so is an id given to a route without one or left off a route that needs it. a first argument that is not a string written whole, such as a name bound to one, is refused with the form to write instead.

a template names a route the same way, a href=(path_to "notes/show" r.id), and the views guide shows it.

keeping an old URL

an app that must keep an old path working declares legacy_route_aliases in one of its modules: a list of calls to routes/moved, each naming an old path and the action that answers it now. the name says what it is, a measure for compatibility, and each alias answers with a permanent redirect (308) to its action's route, so a resource keeps one URL.

spec/runs/aliases/legacy.kso
import "../../../routes"
import "./entries"

pub legacy_route_aliases = [
  (routes/moved "/entry/:id" entries/show)
  (routes/moved "/signbook" entries/index)
  (routes/moved "/sign" entries/create)
]

the action is code, so the compiler resolves entries/index as it resolves any name, and a misspelled one is an unknown name. an alias takes its method from its action's route: entries/index answers GET, so /signbook is a GET, and entries/create answers POST, so /sign is a POST. there is no method to write, so there is none to get wrong.

the derivation reads each call where it is written, as it reads a call to path_to. the old path is written whole as a string that starts with /; the action is a route that is not nested; the path takes :id as its second segment exactly when the route does; and no alias answers a request that a route or another alias answers. each mistake is a compile error at the call:

kanso check, in spec/errors/alias_without_id
error[derive]: `/entry` has no `:id`, but `entries/show` takes one
  --> ./legacy.kso:4:30
   4 | pub legacy_route_aliases = [(routes/moved "/entry" entries/show)]
                                    ^

a query string

a route is found by its path alone, so /search?q=two%20words&page=3 reaches the action GET /search names. the action reads the query with web/query req, which answers it as a form, and web/value reads a field from it as it reads a posted one. a field the query does not carry reads as "". the server sets the query aside when it parses the request, under a header name of its own, and a header of that name sent by the client is replaced, so a client cannot pass a query off as one it did not send.

spec/serve/queried/search.kso
import "../../../web"
import "std/net/http"

# What the action read from the query string.
pub fn index req _
  q = web/query req
  shown = "q={web/value q "q"} page={web/value q "page"}"
  effect (http/text_page "{req.path}: {shown}")

senro's spec asks for that path, for /search with no query, and for /search with a forged header, and the action answers:

spec/serve/queried.out
/search: q=two words page=3
/search: q= page=
/search: q= page=

answering JSON

an action can answer JSON as well as a page, as Rails' respond_to lets one. web/wants_json? req says whether the request asks for it: its path ends .json, or its Accept header names application/json. the route is found by the path without the .json, so /notes.json and /notes/3.json reach the actions /notes and /notes/3 do. web/json status value answers the value as JSON, as render json: does. the value is usually a map a model gives, or a list of them; the generators guide shows the scaffold's two actions that answer this way.

web/web.kso
# `answer` as JSON with `status`, as Rails' `render json:` answers: a map or
# a list of maps, such as a model's `note_attributes` gives.
pub fn json status answer
  http/respond status [json_type] "{json/encode answer}\n"

json_type = "content-type: application/json; charset=utf-8"

# Whether the request asks for JSON, as Rails' `respond_to` reads `format`:
# its path ends `.json`, or its Accept header names `application/json`. The
# route is matched without the `.json`, so `/notes.json` and `/notes/3.json`
# reach the actions `/notes` and `/notes/3` do.
pub fn wants_json? req
  accepted = blank_if_none req.headers["accept"]
  ends = text/ends_with? req.path ".json"
  ends or length (text/split accepted "application/json") > 1

what senro's routing does not have

a Rails routes file can say several things that senro's conventions have no way to say.

  • namespaces and scopes. there is no namespace :admin and no shared prefix such as /api/v1. a module's path is its name.
  • renamed paths. there is no path: "p". a resource named photos lives at /photos.
  • nesting deeper than one level. a module nests under one parent, as described above.
  • constraints, subdomains and mounted engines. a route is found by its method and path alone.
  • a route declared by hand. the only path that is not a resource's is an alias, and an alias only redirects to a resource's route. a webhook with a URL fixed by somebody else is served by a resource at that path, or, when the path cannot be a resource's, by a proxy in front of the app.

what the derivation writes

derive app/conventions, through routes/rest, writes one constant, routes, a map from each method and path to its action, and holds each path_to an app writes, in its code and in its templates, to that table. kanso derived prints what the derivations wrote, and the table is the line that begins routes =. two of the notebook's rows:

kanso derived, in examples/notebook
"GET /notes":{ "action":notes/index "id":"" "name":"notes/index" "secret":"made at random by generate authentication" }
"GET /notes/:note_id/pages/:id":{ "action":pages/show "id":"int" "name":"pages/show" "secret":"made at random by generate authentication" "within":"int" }

each row holds the function the request reaches, its name for path_to, how its own id is read ("" for a route with none, "int" for an annotated one), and, for a nested route, how the parent's id is read, under within. secret is the one the app signs its sessions with, from session.kso; every row carries it, so the action can read the visitor's session. senro routes prints the same table as the columns shown at the top of this guide.
