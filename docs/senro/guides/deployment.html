configuration and deployment

a senro app is configured in two places. what differs from one machine to the next, such as the database and the mail server, comes from the environment. what is true of the app wherever it runs, such as its port and its limits, is written in its code. this guide lists both, then builds the app into one file and runs it.

the environment

an app reads these variables when it starts, or when it first needs one.

variable, what it sets, and its value when unset
PGHOST                 the database's host                127.0.0.1
PGPORT                 its port                           5432
PGUSER                 the role to connect as             postgres
PGDATABASE             the database                       the role's name
PGPASSWORD             the role's password                ""
SENRO_URL              the site, for links in mail        http://127.0.0.1:3000
SENRO_MAIL             how mail is sent                   standard error
SENRO_STORAGE          where uploads are kept             storage
SENRO_PASSWORD_ROUNDS  the cost of a password digest      100000
SENRO_ONLY             "migrate" stops after migrating    unset

the five PG variables are the ones libpq reads, so an app connects wherever its host already points them. a password of "" is for a server that trusts the connection, as a development container's Postgres does. any other password is sent by SCRAM-SHA-256, which never puts the password itself on the wire.

pg/pg.kso
# A session with the Postgres the environment names, as libpq reads it:
# PGHOST, PGPORT, PGUSER, PGDATABASE and PGPASSWORD, each with libpq's
# default when it is unset or empty. An app that connects this way runs
# against whatever database its host sets, with nothing to edit.
pub from_env = os/env "PGHOST" .> (h -> port_from (or_default h "127.0.0.1"))

SENRO_URL matters as soon as the app sends mail with a link in it, because the link is built from it and from nothing a request carries. mailers covers that and SENRO_MAIL.

SENRO_PASSWORD_ROUNDS is how many rounds of PBKDF2 a new password digest is stretched by. the default is 100,000. each digest records its own rounds, so changing the number leaves the passwords already kept working. senro's specs lower it so that signing in is quick; a production app leaves it unset or raises it.

what the app's code says

the rest is in the app, where a change to it is reviewed and versioned with everything else.

  • the port. app/run serves on the port PORT names, 3000 when it is unset.
  • the session secret. senro generate authentication writes 32 random bytes into session.kso as secret. it signs every session and every link the app mails, so keep the file out of a public repository, and know that changing it signs every visitor out.
  • limits. a module's rate_limits says how often one client may call an action.
  • who gets in. without_sign_in and admits are declarations in each module, covered in sessions and sign-in and authorization.
  • the schema. the migrations are compiled into the app. there is no separate schema file to deploy.

the notebook's entry ends with the part a deploy cares about. the database comes from the environment, every action asks for a sign-in unless its module says otherwise, and app/run serves on PORT:

examples/notebook/main.kso
derive app/conventions

# The database comes from PGHOST, PGPORT, PGUSER, PGDATABASE and
# PGPASSWORD, as libpq reads them, so the app runs wherever its host
# sets them.
connected = pg/from_env

# Every action asks for a sign-in unless its module lists it in
# `without_sign_in`.
signed = web/requiring_sign_in routes session/signed_against

app/run "notebook" signed connected derived

building

senro server compiles the app and runs it, which suits development. a deploy builds a binary once and copies it to where it runs.

shell
$ cd notebook
$ kanso build . --release
built ./notebook (llvm ir at notebook.ll)

kanso build . --release writes one native file named for the app's directory. the views, the routes, the migrations and senro itself are compiled into it. the machine it runs on needs no kanso and no copy of the source.

three things stay outside the binary, in the directory it is started from.

  • public/ holds the files the server hands out as they are: stylesheets, images, and the browser modules of an app that has components.
  • storage/ holds uploaded files, unless SENRO_STORAGE names another directory.
  • the environment, as above.

a deploy

the entry migrates the database, checks the schema against what the app was compiled for, and then serves. starting the new binary is therefore a complete deploy for a small app. a deploy that wants the migration to finish before the old server stops runs it as its own step: with SENRO_ONLY=migrate the app migrates, says so and exits, without opening a port. that is what senro migrate does in development.

shell
$ SENRO_ONLY=migrate ./notebook
migrated
$ ./notebook
senro on port 3000

a migration that was edited after it ran stops the app at that step, before it serves anything, and says which one. migrations covers why.

the server speaks HTTP. in production it sits behind a proxy that holds the certificate and forwards requests to its port, as a Rails app sits behind nginx or a load balancer.

what a running app uses

a server keeps four database sessions for requests and lends one to each request while it is answered. each worker beside the server holds one more, and so does the listener that tells open pages about changes. a request that finds all four lent waits for one to come back.

several servers can run against one database. the jobs table hands each job to one worker, however many there are. a rate limit is counted in each server's memory, so two servers each allow the limit; an app that needs one count for all of them puts the limit in the proxy. uploaded files are on disk, so servers that share uploads share the storage directory.

logs

the server writes a line to standard output for each request it answers, and writes failures and each job's outcome to standard error. it keeps no log files of its own; whatever runs the binary collects the two streams.

a server's two streams
senro on port 3000
GET /notes 200 in 2ms
POST /resets 303 in 3ms
senro jobs: ran deliver
