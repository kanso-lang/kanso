senro guides

testing

a senro app's tests are specs that sit beside its modules, in files named <something>_test.kso. an example asks the app for a page the way a browser does and looks at what came back. the request goes straight to the route table the app serves, with no server started and no socket opened. this guide covers what the generators write, how to run it, and how to write more.

what a generator writes

senro generate scaffold note title:text pages:int writes a spec for the notes beside the module that serves them. it lists them, makes one, changes it, sends a page count that is no number, and removes one.

examples/notebook/notes_test.kso
import "../../visit"
import "./given"
import "std/expect"
import "std/spec"

# The notes, asked for as a browser asks. `senro test` runs these against
# the test database, and each example runs in a transaction that is rolled
# back, so none of them sees what another wrote.
test_notes = describe "notes" [
  around (visit/within routes connected)
  it "are listed" listed
  it "are made from the form and shown" made
  it "are changed from the form" changed
  it "are not made from a field that breaks its rule" refused
  it "are gone once removed" removed
]

fn listed v
  visit/get v "/notes" .> (v -> effect (expect v.status . to (equal 200)))

fn made v
  visit/post v "/notes" given/note
    .> (v -> visit/followed v)
    .> (v -> effect (expect v.body . to (contain "milk")))

fn changed v
  visit/post v "/notes" given/note
    .> (v -> visit/patch v (visit/location v) edited)
    .> (v -> visit/followed v)
    .> (v -> effect (expect v.body . to (contain "bread")))

fn refused v
  visit/post v "/notes" broken
    .> (v -> effect (expect v.status . to (equal 422)))

fn removed v
  visit/post v "/notes" given/note .> (v -> gone v (visit/location v))

fn gone v at
  visit/remove v at
    .> (v -> visit/get v at)
    .> (v -> effect (expect v.status . to (equal 404)))

edited = put given/note "title" "bread"

broken = put given/note "pages" "many"

the map an example posts comes from the app's given module, which holds one map for each model: what a form sends to make one. a generator adds its model's map there. it is the app's to edit, like everything else a generator writes, and a spec of your own can read the same maps.

examples/notebook/given.kso
# What the app's specs make rows from: a map for each model, holding what a
# form sends to make one. The generators add a model's map here, and a spec
# reads it as `given/<model>`.
pub note = { "pages":"3" "title":"milk" }

pub page = { "body":"milk" }

pub reading = { "minutes":"3" "title":"milk" }

senro generate resource writes a spec of its API in the same shape, and senro generate authentication writes one of signing in, which is further down this page.

running them

senro test runs every spec in the app, and senro test notes_test.kso runs one file. this is the notebook example, whose specs are the ones its generators wrote:

  are changed from the form
  are gone once removed

the command exits with a failure when any example fails, so it can gate a build. a failing example is named by its full description, with what it answered beside what was expected.

tests have a database of their own. its name is the app's with _test after it, so the rows you typed while trying the app are never in a test's way. senro test makes that database when the server has none by the name, brings it up to the app's migrations, and then runs the specs. the first run of a new app needs nothing set up beyond the Postgres the app already uses.

passwords are stretched by one round while tests run, as Devise sets its stretches to one in a Rails app's tests. the specs run on kanso's interpreter, where the rounds an app ships with would take minutes for each sign-up.

the shape of a spec

a spec is a constant whose name begins test_. describe takes a name and a list, one item to a line. it names an example and the function that runs it. context is a group inside a group, and groups nest as deep as you like. the example passes when its function answers what an expectation answers for a match, and expect value . to (matcher) is how one is written. std/expect has equal, contain, have_length, start_with, end_with, be_none, be_true, be_false and satisfy, and not_to for the opposite.

the spec senro generate authentication writes has all of these. the around hook opens the transaction every example runs in, which is described below. the context inside it holds four examples, and its before runs joined for each of them, after the around and before the example's own function:

examples/notebook/session_test.kso
# Signing in, asked for as a browser asks. `signed` is the app as the entry
# serves it, with the sign-in requirement around its routes, so an example
# meets the door a visitor meets. A visit keeps the cookies the app sets:
# the examples under "with an account" begin signed in, since `joined` makes
# the account, follows the link mailed to confirm its address, and signs in.
test_signing_in = describe "signing in" [
  around (visit/within signed connected)
  it "is asked of a stranger" turned_back
  it "waits for the address to be confirmed" held_back
  context "with an account" [
    before joined
    it "opens the app" opened
    it "is over once the visitor signs out" over
    it "takes the address and password again" returned
    it "refuses a wrong password" refused
  ]
]

senro test prints the groups indented, as in the run above. a failing example is named by its whole description, the names of its groups and its own in order: signing in with an account opens the app.

three hooks set an example up. before takes a function that is handed what the hooks so far built and answers what the example gets. after runs once the example has answered. around is handed the value so far and the rest of the example, and decides what happens on each side of it. a group's hooks wrap those of the groups inside it, and they run afresh for every example, so no example sees what another left. the book's chapter on modules has the whole of it.

a visit

the value a senro example is handed is a visit: one visitor's dealings with the app. visit/get, visit/post, visit/patch and visit/remove each ask for a path and answer the visit as it stands afterwards. visit/post and visit/patch take a map and send it as a form, and visit/post_json sends JSON to an API. the last answer is on the visit: v.status, v.body, and visit/header v "location" for a header. visit/location v is where a redirect points, and visit/followed v goes there.

the notes spec's third example uses most of these. it makes a note from the form, follows the redirect to the note's page, sends the edit form there, and reads the page the app redirects to after the edit:

examples/notebook/notes_test.kso
fn changed v
  visit/post v "/notes" given/note
    .> (v -> visit/patch v (visit/location v) edited)
    .> (v -> visit/followed v)
    .> (v -> effect (expect v.body . to (contain "bread")))

edited = put given/note "title" "bread"

each step answers a new visit, and the next step is handed it. visit/location v after the post is the new note's path, /notes/1 or whatever id the row got, so the example never has to know the id. edited is the note's form with the title changed.

a visit keeps the cookies the app sets and sends them with the next request. an example that signs in is signed in for what it asks next, and a notice set by one answer shows on the page after it. a request goes through everything a served one does: the route table, the check for a form posted from another site, sessions, the sign-in requirement and the page's admits.

the transaction around an example

the first line of a generated spec is its hook:

around (visit/within routes connected)

visit/within opens a database session, begins a transaction, hands the example a visit that has asked for nothing yet, and rolls the transaction back when the example has answered. it rolls back when the example fails too. every example therefore starts from the same database, and they can run in any order. a Rails test is wrapped in a transaction the same way.

routes and connected come from the app's entry: the route table it derives and the effect that opens its database. a test file beside a main.kso reads the names the entry binds, so a spec tests the app as the entry wires it. an entry made with authentication also binds signed, the same routes with the sign-in requirement around them. a spec that passes routes is testing its resource alone, and one that passes signed meets the sign-in page first.

signing in

this is the spec senro generate authentication writes. it uses signed, and a group inside the spec with a hook of its own: every example under "with an account" starts with an account made, its address confirmed, and its visitor signed in. the hook reads the confirmation letter the way the visitor would. visit/mailed v answers the letters the visit's requests have queued, newest first, and visit/link_in letter the path of the first link a letter carries. an example outside the group checks that an account whose address is not confirmed yet is refused.

examples/notebook/session_test.kso
import "../../visit"
import "std/expect"
import "std/list"
import "std/spec"
import "std/text"

fn turned_back v
  visit/get v "/" .> (v -> effect (expect (visit/location v) . to (equal door)))

fn held_back v
  visit/post v "/registration" account
    .> (v -> visit/post v "/session" account)
    .> (v -> effect (expect v.status . to (equal 403)))

fn joined v
  visit/post v "/registration" account
    .> (v -> visit/mailed v .> (letters -> confirmed v (list/first letters)))
    .> (v -> visit/post v "/session" account)

# The link opens a page with a button, and the button's form sends a PATCH
# to the same path without `/edit`.
fn confirmed _ none
  err "making the account mailed no link"

fn confirmed v letter
  visit/patch v (text/replace (visit/link_in letter) "/edit" "") {}

fn opened v
  visit/get v "/" .> (v -> effect (expect v.status . to (equal 200)))

fn over v
  visit/remove v "/session"
    .> (v -> visit/get v "/")
    .> (v -> effect (expect (visit/location v) . to (equal door)))

fn returned v
  visit/remove v "/session"
    .> (v -> visit/post v "/session" account)
    .> (v -> visit/get v "/")
    .> (v -> effect (expect v.status . to (equal 200)))

fn refused v
  visit/remove v "/session"
    .> (v -> visit/post v "/session" mistaken)
    .> (v -> effect (expect v.status . to (equal 422)))

account = { "email":"ada@example.test" "password":"a long password" }

mistaken = put account "password" "another password"

door = "/session/new"

to test a page of your own as a signed-in visitor, put its examples in a group with the same before.

a resource under another

a nested resource needs its parent before any of its paths exist. the generated spec makes one through the parent's model and answers the path under it. v.db is the session the example's transaction is on, so a row made this way is rolled back with the rest.

examples/notebook/pages_test.kso
fn listed v
  pages_path v
    .> (at -> visit/get v at)
    .> (v -> effect (expect v.status . to (equal 200)))

# A note for an example's pages to sit under, and the path to them.
fn pages_path v
  note/create v.db given/note .> (n -> effect "/notes/{n.id}/pages")

the same works for anything an example needs in the database first: call the model with v.db, as an action would.

jobs in a test

a job an action queues waits in the senro_jobs table, inside the example's transaction, until something works it. jobs/worked v.db jobs/default_queue performers t claims one job due at the time t and runs it, as a Rails test's perform_enqueued_jobs does. it answers none when no job was due, and otherwise a line naming the job and how it went, which an expectation can read. performers is the table the entry derives, so a test file beside it has it already. the job's writes happen in the example's transaction and are rolled back with the rest.

spec/db/performed/steps.kso
fn step db table
  time/now
    .> (now -> jobs/worked db jobs/default_queue table (now + 1000))
    .> (said -> print (told said))
    .> (_ -> db)

this is from senro's own suite, which works a queue three times and prints what each step did. it passes a time a second past now, so a job queued for now is due. in an app's spec the database is v.db and the table is performers.

what a spec does not reach

a visit asks for pages and reads them. it does not run the scripts on them, so a live view's updates in the browser and a component compiled to wasm are outside it. senro's own suite drives those in Firefox and Chromium. a single example cannot yet be run by name, only a file.
