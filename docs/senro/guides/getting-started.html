senro guides

getting started

this guide walks through senro's guestbook, the app the framework was first built against. by the end you will know how a senro app is laid out, where each of its decisions lives, and what senro supplies without being asked. it assumes you can read kanso; the tour covers what you need. to start an app of your own instead, the generators write one.

what you need

three things: kanso, built from its repository with cargo build --release; a checkout of senro; and a Postgres server. senro's file .kanso-version names the kanso commit it is tested against. the guestbook expects Postgres on 127.0.0.1:54329 with the user postgres and no password, which is what senro's own specs use.

the shape of an app

an app is a directory. its entry, main.kso, holds the statements that start the app, and each other file beside it is a module. the guestbook has a module per resource (entries, registration, session and the rest), one for each of its two models (signature and account), one for its migrations, and a views directory of templates. the entry imports them all and asks for three conventions.

examples/guestbook/main.kso
import "../../app"
import "../../pg"
import "../../web"
import "./account"
import "./account_mailer"
import "./confirmations"
import "./entries"
import "./home"
import "./migrations"
import "./password"
import "./registration"
import "./removal"
import "./resets"
import "./session"
import "./signature"
import "./unlocks"
import "./views"

derive app/conventions

# The components whose actions run on the server.
served = { "removal":(web/component removal/act removal/view) }

acting = web/components routes served

bound_of = session/signed_against

served_routes = web/requiring_sign_in acting bound_of

connected = pg/from_env

app/run "guestbook" served_routes connected derived

each derive line names a function the compiler runs during the build. kata/views compiles the templates, models/tables folds the migrations into a schema and writes each model's record, reads and writes, and routes/rest places the actions. their output is ordinary kanso, added to the entry before anything is checked; kanso derived examples/guestbook prints it.

the last statement is the app. app/run runs the migrations the database has not run, compares the tables with the schema, and serves on the port PORT names, 3000 when it is unset. because the guestbook has a mailer, a worker beside the server sends the mail it queues. above it, derive app/conventions runs every convention senro has an app follow and hands app/run what they read. the server answers each connection in a fiber of its own and lends each request a database session from a pool. bytes that are not a request, such as a line without a method and a path, are answered 400 Bad Request and the connection is closed.

the schema

the schema is the migrations. each is a file under migrations, named for the moment it was written, and they run in the order of their names. a migration is a value built from a fixed set of changes, so it cannot break when a model changes later, and there is no separate schema file to keep in step with it. this is the guestbook's first.

examples/guestbook/migrations/20261030014602_create_signatures.kso
import "../../../models"

pub create_signatures = models/create_table "signatures" [
  (models/column "name" "text")
  (models/column "message" "text")
]

a model

a model lives in a module named for one row of its table, in the singular as a Rails model is: the signatures table has its model in signature.kso. the models derivation declares the record there, signature, with a field for each column of the table, so the module never lists them, and a field the table lacks cannot be read. the functions in the module are the model's policies and its rules. anyone may sign the book, and only the person who signed an entry may remove it.

examples/guestbook/signature.kso
import "../../models"
import "std/text"

# A signature is a row of the `signatures` table. This module is named for
# the record, so the models derivation declares `signature` here with a
# field for each column and answers for the table by this module's name.
#
# Only the person who signed an entry may remove it. `signature/destroy`
# asks this policy before it deletes anything, and nothing else in the
# guestbook removes a signature.
pub fn destroy? viewer s
  s.name == viewer

# Anyone may sign the book.
pub fn create? _ _
  true

# A signature needs a name and a message, and a message short enough to
# read at a glance.
pub fn problems s
  models/problems [
    (models/rule "name" (text/trim s.name == "") "Say who you are.")
    (models/rule "message" (text/trim s.message == "") "Say something.")
    (models/rule "message" (length s.message > 280) "Keep it under 280.")
  ]

from these, models/tables writes the table's reads and writes into the module, and the app calls them by the module's name. signature/newest db answers the book with the latest signature first, signature/create db fields asks create? and checks problems before it stores a signature, and signature/destroy db id asks destroy? before it deletes one. the models guide lists the rest.

actions and routes

an action is a public function in a resource's module. it takes the request and a database session and answers an effect that yields the response. its name places it: index is GET /entries, create is POST /entries, and the other five of a resource's seven actions follow Rails. a public function with any other name is refused where it is declared.

examples/guestbook/entries.kso
import "../../models"
import "../../routes"
import "../../web"
import "./removal"
import "./signature"
import "./views"
import "std/list"

# The session says who is signed in, and carries a notice across the
# redirect that follows a signature or a sign-in; the page that shows the
# notice clears it.
pub fn index req db
  s = web/session req
  signature/newest db .> (book -> shown req book s (filled "" {}) 200)

# A signature is made through its model, whose rules decide whether it is
# fit to keep. It is signed with the name of the account signed in. The
# fields go to Postgres as parameters, so what a visitor types is stored as
# text and never read as SQL.
pub fn create req db
  viewer = web/viewer req
  f = put (web/input req) "name" viewer
  signature/create db f .> (w -> signed req db w)

neither action writes SQL. index reads the book with signature/newest. create reads who is signed in from the session, which is a cookie signed with the app's secret, and signs the entry with that name. it never sees a visitor who is not signed in: the entry serves every action that its module does not open through web/requiring_sign_in, which sends that visitor to the sign-in page first (the sessions guide has the details). the form goes through the model: signature/create checks the policy and the rules and answers either the new record or the problems to show. the db an action is handed already knows who is signed in, so the policy is asked about that visitor without the action handing the model a viewer.

a view

a view is a kata template. its first line names what it takes, and the rest is indented markup, closed for you: a tag with its classes and attributes, then its text. {viewer} interpolates and escapes, = expr writes a value escaped and == expr writes it raw, and the control lines are if and each: each signatures e -> writes the rows under it once for each signature, with e naming it. kata/views compiles each template to kanso functions and checks each field it reads. signed_view, which entries/index calls, answers the page as a value senro can send as bytes, so its page script can draw the page in the browser with the same template compiled to wasm; a first request gets it drawn as HTML.

running it

from the root of the senro checkout:

shell
kanso run examples/guestbook

open http://localhost:3000, make an account and sign the book. kanso run builds at kanso's development tier; kanso build examples/guestbook makes a release binary, which stretches passwords about fourteen times faster.

the terminal shows the port, then a line for each request as the server answers it: the method, the path, the status and the milliseconds it took. this is a new account being made, confirmed through its mailed link and signed in:

terminal
senro on port 3000
GET / 200 in 3ms
GET /registration/new 200 in 0ms
POST /registration 303 in 7ms
senro jobs: ran deliver
GET /confirmations/:token/edit 200 in 2ms
PATCH /confirmations/:token 303 in 6ms
POST /session 303 in 9ms
GET / 200 in 3ms
GET /nothing-here 404 in 1ms

the method is the one a form stands for, so the confirmation's button reads PATCH. the query string is left out. a signed token in a path is written :token, and an uploaded file's key :key, so a log that is kept holds no link that would confirm an address, reset a password or open a file.
