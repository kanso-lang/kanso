senro guides

authorization

authentication says who a visitor is, and the sessions guide covers it. authorization says what that visitor may do. senro puts the question in two places. a module says who may reach its pages, once, the way a Rails controller's before_action does. a model says who may write a record and which records a viewer may see. this guide covers the first, and how it carries over to the data a page fetches after it has loaded.

who may reach a page

an app behind web/requiring_sign_in asks every action for a visitor who has signed in, except the ones its module lists in without_sign_in. that settles signed in or not. to say more, a module defines admits.

spec/serve/admitted/ledger.kso
import "../../../data"
import "./books"
import "std/net/http"

# Only the bookkeeper, viewer 1, may reach the ledger.
pub fn admits _ viewer _
  effect (viewer == "1")

# The ledger asks the server for the books' total, as a component's action
# would from the browser.
pub fn index _ _
  asks = data/asking? (books/total 3)
  effect (http/text_page "the ledger, which asks the server: {asks}")

admits takes the action's name, the viewer's id and a database session, and answers an effect of true or false. it is asked once a request is past the sign-in, before the action runs. a viewer it refuses is answered 403, and the action does not run. a module with no admits admits whoever the sign-in does.

the first parameter is the action's name, so a module that guards only some actions writes an arm for each and one for the rest. the session asks as the viewer, so a check can read what it needs, such as the viewer's own row, through the models. that is why it answers an effect.

a module that guards one action
pub fn admits "destroy" viewer _
  effect (viewer == "1")

pub fn admits _ _ _
  effect true

what a page asks the server for

a page is not finished when its HTML arrives. a component on it may ask the server for data through a provider, as the views guide describes, and that request arrives on its own, some time after the page. it would be easy to check the viewer again inside every provider, and easy to forget one.

senro answers a provider's request as it would answer the page it came from. the page's script sends the page's path with the request. the server finds that page and checks three things, once for the request, however many providers it calls:

  • the page uses each provider called. this is worked out while the app compiles, from its calls: the page's module must lean on a module that asks for the provider, meaning the module itself or one its calls reach, as an action reaches the component whose action asks.
  • when the page asks for a sign-in, the visitor has one.
  • the page's module admits the viewer, by the same admits the page itself is held to.

so a provider is written with no check of its own for what the page has checked.

spec/serve/admitted/books.kso
# A provider: what the books hold for a number of years, read for whoever
# asks. It checks nothing about the viewer, since the page that asks for it
# has been checked already.
pub fn total viewer _ years
  effect "{years} years of books, read for viewer {viewer}"

senro's spec for this serves a small app. the ledger above admits only viewer 1 and asks for books/total. the desk admits anyone who has signed in, and shows what the ledger shows, so it leans on the ledger's module.

spec/serve/admitted/desk.kso
import "./ledger"

# The desk shows what the ledger shows, to anyone who has signed in, so it
# leans on the module that asks for the books' total.
pub fn index req db
  ledger/index req db

the front page is open to all and asks the server for nothing. the entry names the providers and then puts the table behind the sign-in; either order works.

spec/serve/admitted/main.kso
derive data/providers
derive routes/rest

connected = pg/connect "127.0.0.1" 54329 "postgres" "postgres" ""

answering = web/providers routes books/provided

guarded = web/requiring_sign_in answering web/unbound

web/serve 24420 guarded connected

the spec then sends ten requests and records each answer.

line by line: a visitor who has not signed in asks for the books from the desk, which wants a sign-in, and from the front page, which does not use them, and is refused both times. viewer 2 signs in and asks for the ledger page, and is refused by admits. viewer 2 then asks for the books from the ledger and is refused by the same check; from the desk, and is answered, because the desk admits anyone signed in; from the front page, and is refused because that page does not use them; and without naming a page, and is refused. viewer 1 gets the ledger page, and the books from it. the last request names a provider the app does not have, which is not found.

what stays with the provider

a page decides which providers it calls, and it also chooses their arguments. a page that may list the viewer's own notes could be made to ask for somebody else's by id. that question belongs to the record, and the model answers it: a provider that reads through a model, as every read in an app does, gets only what the model's visible? lets that viewer see, as the models guide describes. the page's check covers whether the viewer may be here, and the model's covers which rows are theirs.

what is not here

a server component's actions, the ones that write to the database from a click without a page load, are open to any visitor and rely on their models' policies to refuse a write. they are not yet answered as their page is.
