senro guides

the command line

senro has one command, senro, as Rails has rails. it makes an app, writes the parts of one, lists its routes, brings its database up to date, serves it and runs its tests. this guide goes through each. the command is a shell script, bin/senro in senro's repository, and it works once that directory is on your PATH.

shell
$ senro
senro: usage: senro new <app>
       senro generate <generator> <word>...   (or `senro g`)
       senro generate                         lists the generators
       senro routes                           lists the routes
       senro server                           (or `senro s`)
       senro migrate
       senro test [file]                      (or `senro t`)

the command runs kanso programs, so it needs kanso. it uses the kanso on your PATH, or the one KANSO names.

a new app

senro new writes an app in a directory named for it: an entry, a home page, a layout and an empty migrations directory. it refuses a directory that is there already.

shell
$ senro new notebook
  create notebook/main.kso
  create notebook/home.kso
  create notebook/migrations/.keep
  create notebook/views/layout.kata
  create notebook/views/home.kata

the entry imports senro by the path from the new app to senro's own directory, so the app compiles where it stands. every other command is run from inside the app.

an app can also name senro's modules by repository, as kanso reads any hako from GitHub, and then it needs no checkout of senro beside it:

main.kso
import "kanso-lang/senro/app"
import "kanso-lang/senro/pg"

derive app/conventions

connected = pg/from_env

app/run "shelf" routes connected derived

kanso install reads the imports, fetches senro's newest release, the highest vX.Y.Z tag on its repository, and writes the version and its commit into hako.lock.

shell
$ kanso install .
installed 1 hako(s):
  kanso-lang/senro v0.3.0

the compiler reads the lock and the cache and never the network, so the app builds offline from then on, against the release the lock names. kanso update moves the lock to a later release, and kanso list shows what it pins.

generators

senro generate, or senro g, writes code. with nothing after it, it lists the generators it can find.

shell
$ senro generate
  scaffold
  resource
  model
  controller
  migration
  mailer
  job
  authentication

each takes words after its name. the generators guide reads what scaffold and authentication write, file by file, and the migrations guide covers migration. in short:

  • scaffold note title:text pages:int writes a whole resource: its model, its migration, the seven actions and three views.
  • resource reading title:text minutes:int writes an API: the model, its migration and five actions that answer JSON.
  • model tag name:text writes a model and its migration, and nothing that serves it.
  • controller pages index show writes a module with those actions and a view for each that shows a page.
  • migration add_rating_to_notes rating:int writes a migration, reading what it does from its name.
  • mailer account welcome writes account_mailer.kso with a function for each letter.
  • job tidy writes tidy_job.kso, a job the worker beside the server performs.
  • authentication adds accounts: signing up, confirming an address by a mailed link, signing in and out, locking an account after a run of wrong passwords and mailing a link that unlocks it, and resetting a lost password by mail.

every generator prints each file it writes or changes. none writes over a file that is there: one that would stops before it writes anything, and says which file.

generators of your own

a generator senro does not ship is a kanso program at generators/<name>.kso, or generators/<name>/main.kso when it needs more than one file. senro looks in the app, and beside each library the app's entry imports by path: an import of ../lib/shop/carts looks in ../lib/shop/generators. so a library can ship the generators that go with it, as a Rails engine does.

the program is run in the app's directory, and the words that followed its name are its arguments. this one says what it was given.

generators/greeting.kso, in the app
import "std/io"
import "std/os"

os/args .> (a -> io/write "greeting: {a}\n")
shell
$ senro generate greeting one two
greeting: ["one" "two"]

senro generate lists it with where it was found. senro's own generators are looked for first, so one from outside cannot take the place of scaffold.

routes

senro routes lists every route the app answers, as rails routes does: the verb, the path and the action. these are the first lines for the notebook, after two scaffolds.

shell
$ senro routes
GET     /                               home/index
GET     /notes                          notes/index
POST    /notes                          notes/create
GET     /notes/new                      notes/new
GET     /notes/:id                      notes/show
PATCH   /notes/:id                      notes/update
DELETE  /notes/:id                      notes/destroy
GET     /notes/:id/edit                 notes/edit

behind a sign-in, a route that asks for none is marked open, and one that counts its calls is marked limited.

later lines, once the app has accounts
POST    /registration                   registration/create  open
POST    /session                        session/create       open, limited
DELETE  /session                        session/destroy

the routes are not written anywhere to be listed. an action's name places it, as the routing guide describes, and the table is worked out while the app compiles. so the command compiles the app and reads the table; it opens no database. an app that does not compile says why instead.

migrate and server

senro migrate brings the database up to the app's migrations, checks the tables against the schema the app was compiled with, and stops. senro server, or senro s, does the same and then serves on port 3000. both run the app itself, so they read the same PGHOST, PGPORT, PGUSER, PGDATABASE and PGPASSWORD it does.

shell
$ senro migrate
migrated
$ senro server
senro on port 3000

a table that differs from the schema stops both before anything is served, with each difference named. the models guide says what is compared.

test

senro test, or senro t, runs the specs in the app's *_test.kso files, and senro test notes_test.kso runs one file. it works on a database of its own, the app's with _test after its name, which it makes when the server has none by that name and migrates before anything runs. it exits with a failure when an example fails. the testing guide covers what a spec holds.

shell, in examples/notebook
$ senro test notes_test.kso
senro: made the database `notebook_test`
notes
  are listed
  are made from the form and shown
  are changed from the form
  are not made from a field that breaks its rule
  are gone once removed

5 examples, 0 failed
test_notes ... ok
1 passed, 0 failed

the first line appears only on the run that makes the test database.
