senro guides

security

this guide goes through the attacks a web app has to expect and says what senro does about each, as the Rails security guide does for Rails. most of the defences are on without being asked for. where one is the app's to turn on or to get right, the section says so. the guides it links to cover each mechanism in full.

sessions

a session is a cookie the app signs with its secret, an HMAC-SHA-256 over what the cookie holds. a visitor can read their session and cannot change it: a cookie whose signature does not match is treated as no session at all. the secret is the 32 random bytes senro generate authentication writes into session.kso. keep that file out of a public repository.

the cookie is HttpOnly, so a script on the page cannot read it, and SameSite=Lax, so a browser does not send it with a form another site posts. when the request reached the server through a proxy that took it over HTTPS and said so in X-Forwarded-Proto, every cookie in the answer is also marked Secure, and the browser never sends it back in the clear.

one answer, to a plain request and to one a proxy took over HTTPS
set-cookie: senro_notice=Noted%3B%20thank%20you.; Path=/; HttpOnly; SameSite=Lax
set-cookie: senro_notice=Noted%3B%20thank%20you.; Path=/; HttpOnly; SameSite=Lax; Secure

a sign-in lasts fourteen days. it is also tied to the password it was made with: the session keeps a fingerprint of the account's digest, and the server compares it at every request. changing a password therefore ends every sign-in made under the old one, on every device. sessions and sign-in covers the cookie and the sign-in.

requests from other sites

a page on another site can make a visitor's browser post a form to yours. senro refuses any request that would change something and says it came from elsewhere. a browser names the origin of a request in Sec-Fetch-Site, and an older one in Origin, and anything but the app's own origin is answered 403 before an action runs. there is no token to put in each form and none to forget.

web/web.kso
# A request that would change something, sent by a page on another site, as
# Rails' `protect_from_forgery` refuses one. The session cookie is
# SameSite=Lax, so a browser should not send it on such a request at all;
# this refuses the request even when it does. A browser says where a
# request came from in `Sec-Fetch-Site`, and in `Origin` when it is older
# than that header: anything but the app's own origin is refused. A request
# with neither header comes from a program, not a page, and is let through.
fn forged? method req
  return false if method == "GET" or method == "HEAD"
  elsewhere? req.headers["sec-fetch-site"] req

a request with neither header comes from a program such as curl, which holds no visitor's cookies to misuse, and is let through. a GET is never checked, so an action reached by GET must not change anything. the routing convention gives GET only to the actions that read.

passwords

a password is kept as a PBKDF2-SHA-256 digest with a salt of its own and 100,000 rounds, written with its rounds beside it so the number can rise without breaking the digests already kept. checking one compares every byte of the two digests whichever differs first, so the time a refusal takes says nothing about how close a guess was.

passwords/passwords.kso
# Whether `password` is the one `kept` was digested from. A digest this
# module did not write matches nothing. The two digests are compared over
# every byte, whichever differs first, so the time a refusal takes says
# nothing about how much of a guess was right.
pub fn matches? password kept
  parts = text/split kept "$"
  return false if length parts != 4
  return false if parts[1] != "pbkdf2-sha256"
  rounds = text/to_int parts[2]
  salted? password rounds (base64/decode parts[3]) parts[4]

signing in with an address that has no account still checks the password, against a stand-in digest that nothing matches. the answer and the time it takes are the same as for a wrong password, so the sign-in form cannot be used to learn which addresses have accounts.

guessing

two limits slow a guesser down, and they count different things. a module's rate_limits counts calls from one address: the generated sign-in allows ten tries in three minutes and answers 429 after that. the account's own count of wrong passwords does not care where they came from: five in a row lock the account for an hour, and a right password is told so while a wrong one is answered as any wrong password is. the first stops one machine hammering the form. the second stops many machines sharing the work.

links in mail

a link that resets a password or confirms an address carries a signed token: the account's id, the moment the link stops working, and an HMAC over both, the link's purpose, and a value the account holds now. nothing is stored. a reset token is signed over the digest the reset will replace, so it works once, and the purpose keeps a token made for one kind of link from opening another.

the link's host comes from SENRO_URL and never from the request's Host header, which the sender of a request chooses. the server's log writes a token in a path as :token and leaves query strings out, so a log can be read by people who should not be able to reset an account. mailers covers the links.

injection

SQL. an app's modules hold no SQL. reads and writes go through its models, which send every value to Postgres as a parameter beside the statement and never as part of its text. a value a visitor typed cannot become SQL, because nothing an app writes assembles a statement from text.

HTML. a kata template escapes what it writes. = expr and {expr} in text both turn <, >, & and quotes into entities. writing a value raw takes a different operator, ==, which the layout uses for the page body it was handed. a search of an app's templates for == finds every place raw HTML can enter.

mail headers. a message whose subject or address holds a line break is refused before it is sent or queued, so text from a form cannot add a header such as Bcc.

paths. a request for a static file whose path holds .. is answered 404 without touching the disk.

uploads

an uploaded file is stored under a random key and served back from /senro/blobs/<key> with X-Content-Type-Options: nosniff and a Content-Disposition that names it, so a browser does not guess a type the uploader did not declare. a request whose body would be larger than 10 MiB is answered 413 before the body is read. file uploads covers the rest.

who may do what

authentication says who the visitor is. three checks then decide what they may do, each written once.

  • the entry's web/requiring_sign_in sends a visitor who has not signed in to the sign-in page from every action a module does not list in without_sign_in. a new action is closed until someone opens it.
  • a module's admits action viewer db says who may reach each of its pages, and covers the data the page loads afterwards.
  • a model's policies, create?, update?, destroy? and visible?, are asked by the model on every read and write, whichever action it came from. an action cannot forget to ask, because the write it calls is the one that asks.

the policies a scaffold writes let anyone write. narrow them before the app is public. authorization and models cover the three.

what is left to the proxy

senro's server speaks HTTP. the proxy in front of it holds the certificate, redirects plain requests to HTTPS, and sends the Strict-Transport-Security header if the site wants one. it must also set X-Forwarded-Proto, which most do, for the cookies to be marked Secure.
