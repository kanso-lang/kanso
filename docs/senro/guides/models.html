models and migrations

a senro app keeps its data in Postgres. this guide covers where the schema comes from, how a model is tied to a table, the policies that guard each write, and the rules that decide whether a record is fit to keep.

migrations are the schema

an app's migrations are a list of values in one module, oldest first. each is built from a fixed set of changes, models/create_table and models/add_column here, so a migration written a year ago cannot break when a model changes today.

examples/guestbook/migrations.kso
import "../../models"

# The guestbook's schema, as the changes that built it, oldest first. The
# models derivation folds these into the schema the app is compiled against.
pub all = [signed joined emailed confirmable]

signed = models/create_table "signatures" [id name message]

id = models/column "id" "serial"

joined = models/create_table "accounts" [id name digest]

# The address a reset link is sent to.
emailed = models/add_column "accounts" email

# When the address was confirmed, or empty until it is.
confirmable = models/add_column "accounts" confirmed

name = models/column "name" "text"

message = models/column "message" "text"

digest = models/column "digest" "text"

email = models/column "email" "text"

confirmed = models/column "confirmed" "text"

derive models/tables folds the list into the schema while the app compiles. there is no schema file to keep in step, and no command to regenerate one. the entry runs models/made schema as it starts, which creates each table that is missing, and then models/compared db schema, which reads the live tables and refuses to serve if a column's name, type or nullness differs or a table is missing. defaults and constraints are not compared.

a schema that needs SQL the fold cannot read, a trigger for instance, is checked in as pg_dump --schema-only output, in schema.sql beside the entry. the schema is then read from its CREATE TABLE blocks instead of the migrations.

a model is a record type

a record type in a module is a model when its name matches a table: signature reads signatures. every field must be a column. a misspelled field stops the build, with the error at the type.

spec/errors/field_without_column/notes.kso
pub type note
  bdoy

pub fn shown n
  n.bdoy
kanso check
error[derive]: `bdoy` is not a column of `notes`
  --> ./notes.kso:1:10
   1 | pub type note
                ^

a type named after no table is refused the same way. for each model the derivation writes a reader into the model's module, signature_from row, which builds a record from a row a query answered and takes each field from the column of the same name.

policies

a model's module says who may change its rows. create?, update? and destroy? each take the viewer and the record and answer true or false. the guestbook lets anyone sign and only the signer remove:

examples/guestbook/signatures.kso
import "../../models"
import "std/text"

# A signature as the `signatures` table stores it. senro/models checks each
# field against the table's columns and writes `signature_from`, which builds
# one from a row.
pub type signature
  id
  name
  message

# Only the person who signed an entry may remove it. The models derivation
# reads this policy and writes `signature_destroyed`, which asks it before it
# deletes anything, so there is no other way to remove a signature.
pub fn destroy? viewer s
  s.name == viewer

# Anyone may sign the book.
pub fn create? _ _
  true

# A signature needs a name and a message, and a message short enough to
# read at a glance.
pub fn problems s
  models/problems [
    (models/rule "name" (text/trim s.name == "") "Say who you are.")
    (models/rule "message" (text/trim s.message == "") "Say something.")
    (models/rule "message" (length s.message > 280) "Keep it under 280.")
  ]

the derivation describes each model as a value, signature_model, and the writes take it. models/created viewer db model fields reads the fields into a record, asks create?, checks the rules, and inserts only when both pass. models/updated and models/destroyed read the row first, ask their policy, and write only on a yes, answering web/denied or web/absent otherwise. a model with no such policy cannot be written this way, so writes default closed.

reads default open. a module may declare visible?, and models/shown viewer model rows keeps the records a query answered that the viewer may see; without it every row shows. a missing read policy can show a row but never change one.

rules

problems takes a record and answers models/problems of a list of models/rule field broken message. models/created and models/updated check it, the second on the record as the change leaves it. a record that breaks a rule comes back as models/invalid, holding each broken field's message and the record as given, so the action can answer the form again with both. the guestbook's entries/create does that with a 422:

examples/guestbook/entries.kso
import "../../models"
import "../../pg"
import "../../web"
import "./removal"
import "./signatures"
import "./views"
import "std/list"

# A signature is made through its model, whose rules decide whether it is
# fit to keep. It is signed with the name of the account signed in. The
# fields go to Postgres as parameters, so what a visitor types is stored as
# text and never read as SQL.
pub fn create req db
  viewer = web/viewer req secret
  f = put (web/form req.body) "name" viewer
  models/created viewer db signatures/signature_model f
    .> (w -> signed req db w)

# A signature the rules turned back: the page again, answered 422, with the
# form as the visitor filled it in and what to fix.
fn signed req db w:models/invalid
  s = web/session req secret
  form = filled w.record.message w.problems
  pg/query db newest [] .> (r -> shown req r.rows s form 422)

# A signature kept. The answer sends the browser back to the list, so
# reloading it does not sign the book again.
fn signed req _ _
  thanked = put (web/session req secret) "flash" "Thank you for signing."
  effect (web/kept (web/redirect "/") secret thanked)

queries

a query is SQL with numbered parameters, sent through pg/query db sql args. what a visitor types goes to Postgres as a parameter and is never read as SQL. senro speaks Postgres's wire protocol in a client written in kanso, logs in with SCRAM-SHA-256, and secures the connection with TLS when pg/connect_tls asks for it.
