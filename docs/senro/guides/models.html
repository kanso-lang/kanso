senro guides

models and migrations

a senro app keeps its data in Postgres. this guide covers where the schema comes from, how a model is tied to a table, the calls an action reads and writes it with, the policies that guard each write, and the rules that decide whether a record is fit to keep.

migrations are the schema

an app keeps its migrations one to a file, in migrations. a file is named <stamp>_<name>.kso, where the stamp is the moment it was written, and holds one constant, <name>: a change or a list of changes. each is built from a fixed set of changes, models/create_table and models/add_column here, so a migration written a year ago cannot break when a model changes today. the migrations guide covers the files, their order and the generator that writes them.

examples/guestbook/migrations/20261030014602_create_signatures.kso
import "../../../models"

pub create_signatures = models/create_table "signatures" [
  (models/column "id" "serial")
  (models/column "name" "text")
  (models/column "message" "text")
]

a later migration changes a table that is there. this one adds two columns to accounts, and keeps the kind they share under a name of its own.

examples/guestbook/migrations/20261105065821_add_lock_to_accounts.kso
import "../../../models"

# How many wrong passwords in a row the account has had, and when too many
# of them locked it, or empty while it is open.
pub add_lock_to_accounts = [
  (models/add_column "accounts" failures)
  (models/add_column "accounts" (models/column "locked" blank_text))
]

failures = models/column "failures" "integer not null default 0"

derive models/tables folds the files, in the order of their names, into the schema while the app compiles. there is no schema file to keep in step, and no command to regenerate one. the entry runs models/migrated db app migrations/all as it starts, where all is the same files in the same order, written into the module by the derivation. it runs the migrations the database has not yet run and records each in a senro_migrations table under the app's name and its stamp, beside the SQL it ran, as Rails records them in schema_migrations. a migration runs once, and one whose SQL has changed since it ran stops the app, naming it, so a new change is a new migration. each change does nothing when its work is already done, so a database made before migrations were recorded takes them safely the first time. then it runs models/compared db schema, which reads the live tables and refuses to serve if a column's name, type or nullness differs or a table is missing. defaults and constraints are not compared.

a table that lists models/timestamps among its columns gets created_at and updated_at, the two columns Rails' t.timestamps adds. each is timestamptz not null default now(), so Postgres sets both when a row is made. a change written through the model sets updated_at, and neither making a record nor changing one takes a form's value for either column, so a request cannot backdate a row. the two are also models/created_at and models/updated_at, one at a time, which is how the scaffold ends every table it makes.

spec/db/stamped/migrations.kso
notes = models/create_table "notes" (list/concat [id body] models/timestamps)

models/add_unique_index table column gives a column a unique index, as Rails' add_index with unique: true does, and generate authentication gives users.email one. the derivation reads the index from the migrations, or from a unique index or constraint over one column in schema.sql, and the model names the column. the model's create then inserts with on conflict do nothing, so when two requests race for one address, the one that loses answers models/invalid with "That is taken." on the field rather than an error. its update asks before it writes.

spec/db/unique/migrations.kso
accounts_handle = models/add_unique_index "accounts" "handle"

a schema that needs SQL the fold cannot read, a trigger for instance, is checked in as pg_dump --schema-only output, in schema.sql beside the entry. the schema is then read from its CREATE TABLE blocks instead of the migrations.

a model is a module named in the singular

a module named for one of a table's rows holds the table's model, as a Rails model is named in the singular: the guestbook's signature.kso is the model of signatures. the derivation declares the record in it, signature, with a field for each column in the table's order, and the module's functions read s.name and s.message as they read any record's fields. the record is checked like code someone wrote, so a field the table lacks is an error where it is read. the entry imports the module, since a derivation reads the modules the entry names. kanso derived prints the declaration with the rest of what the derivation writes:

kanso derived examples/guestbook
# in signature, by models/tables
pub type signature
  id
  name
  message
  photo

a module may declare the record itself, to leave a column out of it. every field it names must then be a column. a misspelled field stops the build, with the error at the type.

spec/errors/field_without_column/notes.kso
pub type note
  bdoy

pub fn shown n
  n.bdoy
kanso check
error[derive]: `bdoy` is not a column of `notes`
  --> ./notes.kso:1:10
   1 | pub type note
                ^

a type named after no table is refused the same way. for each model the derivation writes a reader into the model's module, signature_from row, which builds a record from a row a query answered and takes each field from the column of the same name. it writes signature_attributes s too, the record as a map from each field's name to its value, as Rails' attributes gives one. web/json writes that map as a JSON object. a module that declares signature_attributes itself keeps its own, so a model can leave a field out of what it shows.

reads and writes by name

an action reads and writes through its model by name and writes no SQL. the derivation writes the calls into the model's module, so the module answers for its table as a Rails model answers its class methods. for the model in note.kso:

callanswers
note/find db idthe record, or none
note/find_by db "title" tthe first record whose field holds the value, or none
note/all dbevery record, oldest first
note/newest dbevery record, the one made last first
note/ordered db "title"every record in the order of a column
note/where db "title" tthe records whose field holds the value
note/paged db number perone page of the records, oldest first
note/paged db "author" a number perone page of the records whose field holds the value
note/create db fieldsthe record as stored, or models/invalid
note/update db id changesthe record as changed, or models/invalid
note/destroy db idthe record as it was
note/increment db id "views"the record after one is added to the column

no call takes a viewer, because the db senro hands an action already knows who is signed in. the web layer names the viewer on the session before an action, a server component or a provider sees it, and a session nobody named asks as a visitor. a read shows what the model's read policy allows that viewer, and a write asks the model's policies about the same viewer. the next section covers the policies.

a field or an order named in a call goes into the SQL senro writes, so it must be one of the table's columns. one written out in the call is checked against the columns when the app is checked, and the error is at the call:

spec/errors/order_not_a_column/main.kso
# An order written out that the comments table does not have, asked of the
# model by its module's name.
pg/connect "127.0.0.1" 54329 "postgres" "postgres" ""
  .> (db -> comment/ordered db "written_at")
  .> (cs -> print cs)
kanso check
error[derive]: `written_at` is not a column of `comments`: it has id, post_id, body, author
  --> ./main.kso:11:13
  11 |   .> (db -> comment/ordered db "written_at")
                   ^

a field or an order that arrives in a variable is checked when the call runs, before any SQL is sent, and one that names no column is an error there.

a module that declares a function of one of these names keeps its own, so a resource's actions and its model sit in two modules: notes/create is the action, and note/create is the write it calls. a module that holds two models gets none of the calls, since a bare find would not say which model it meant.

policies

a model's module says who may change its rows. create?, update? and destroy? each take the viewer and the record and answer true or false. the guestbook lets anyone sign and only the signer remove:

examples/guestbook/signature.kso
import "../../models"
import "std/text"

# A signature is a row of the `signatures` table. This module is named for
# the record, so the models derivation declares `signature` here with a
# field for each column and answers for the table by this module's name.
#
# Only the person who signed an entry may remove it. `signature/destroy`
# asks this policy before it deletes anything, and nothing else in the
# guestbook removes a signature.
pub fn destroy? viewer s
  s.name == viewer

# Anyone may sign the book.
pub fn create? _ _
  true

# A signature needs a name and a message, and a message short enough to
# read at a glance.
pub fn problems s
  models/problems [
    (models/rule "name" (text/trim s.name == "") "Say who you are.")
    (models/rule "message" (text/trim s.message == "") "Say something.")
    (models/rule "message" (length s.message > 280) "Keep it under 280.")
  ]

each write asks its policy first. signature/create db fields reads the fields into a record, asks create?, checks the rules, and inserts only when both pass. update and destroy read the row first, ask their policy, and write only on a yes. a no answers web/denied, and an id no row has answers web/absent. a model with no such policy cannot be written this way, so writes default closed.

a write no viewer is behind is made as the app. account/update (models/as_app db) id { "failures":"0" } asks no policy. the guestbook writes this way when a sign-in counts a wrong password and when a reset link sets a digest, and the sessions guide gives the rule for it. increment asks update? as update does. it adds one in the statement that answers the record, so requests that count at once each see a count of their own.

reads default open. a module may declare visible?, and each read then answers only the records it says the viewer may see; without it every row shows. a missing read policy can show a row but never change one.

rules

problems takes a record and answers models/problems of a list of models/rule field broken message. the model's create and update check it, the second on the record as the change leaves it. senro writes the rules a Rails model reaches for first. models/present field value is presence: true, and a value of nothing but spaces is as blank as none. models/at_most field n value and models/at_least field n value bound a value's length in characters, as length: { maximum:, minimum: } does. models/one_of field choices value is inclusion: { in: choices }, and the value must equal a choice whole, so a select can post only what the app knows. models/email_address field value asks for one @ with something on each side of it and no spaces. a record that breaks a rule comes back as models/invalid, holding each broken field's message and the record as given, so the action can answer the form again with both. the guestbook's entries/create does that with a 422:

examples/guestbook/entries.kso
# A signature is made through its model, whose rules decide whether it is
# fit to keep. It is signed with the name of the account signed in. The
# fields go to Postgres as parameters, so what a visitor types is stored as
# text and never read as SQL.
pub fn create req db
  viewer = web/viewer req secret
  f = put (web/form req.body) "name" viewer
  signature/create db f .> (w -> signed req db w)

# A signature the rules turned back: the page again, answered 422, with the
# form as the visitor filled it in and what to fix.
fn signed req db w:models/invalid
  s = web/session req secret
  form = filled w.record.message w.problems
  signature/newest db .> (book -> shown req book s form 422)

# A signature kept. The answer sends the browser back to the list, so
# reloading it does not sign the book again.
fn signed _ _ _
  effect (web/noticed (web/redirect "/") "Thank you for signing.")

underneath

the calls by name are written over functions of the models module that take the viewer and the model as arguments. the derivation describes each model as a value for them, signature_model. models/found viewer db model id reads a record by its id and answers none when no row has it or the model's visible? hides it from the viewer, as Rails' find_by(id:) answers nil. models/where viewer db model field value answers the records whose field holds the value, oldest first, that the viewer may see. a post's comments are models/where viewer db comment/comment_model "post_id" id. the field is checked as it is in a call by name. senro's spec calls both, once with a field in a variable that names no column:

spec/db/finders/reading.kso
import "../../../models"
import "./comment"
import "./post"
import "std/list"

pub fn post db id
  models/found "" db post/post_model id .> (p -> said db (titled p))

fn titled none
  "no post"

fn titled p
  "post: {p.title}"

pub fn comments viewer db id
  models/where viewer db comment/comment_model "post_id" id
    .> (cs -> said db "as [{viewer}]: {bodies cs}")

fn bodies cs
  list/to_list (list/map cs (c -> c.body))

pub fn unread db
  field = "author_id"
  models/where "" db comment/comment_model field 1
    .> (cs -> said db "read {length cs}")
    .? (e -> said db "refused: {e.reason}")

fn said db line
  print line .> (_ -> effect db)

the SQL these functions write goes to Postgres through pg, a client written in kanso. it speaks Postgres's wire protocol, logs in with SCRAM-SHA-256, and secures the connection with TLS when pg/connect_tls asks for it. what a visitor types goes to Postgres as a parameter and is never read as SQL.

a foreign key reads both ways

a foreign key the migrations add writes that models/where for the app, once in each direction, as Rails' has_many and belongs_to do. when pages.note_id holds a row of notes, the page module gets of_note viewer db note, the pages of a note that the viewer may see, and the note module gets of_page viewer db page, the note a page belongs to. each reads the other record's field by name, note.id or page.note_id, so neither module imports the other, and an app can import either one into the other without a cycle. a module that already declares a function of that name keeps its own. so does one that declares a pub function or record named as the parameter. an app that keeps a schema.sql gets its keys from the dump's FOREIGN KEY ... REFERENCES constraints instead.

the modules in spec/db/associated hold one helper each and nothing about the other table. the derivation writes the rest:

spec/db/associated/reading.kso
import "../../../models"
import "./note"
import "./page"
import "std/list"

pub fn pages_of db id
  models/found "" db note/note_model id
    .> (n -> page/of_note "" db n)
    .> (ps -> said db "note {id}: {list/to_list (list/map ps page/bodied)}")

pub fn note_of db id
  models/found "" db page/page_model id
    .> (p -> note/of_page "" db p)
    .> (n -> said db "page {id}: {note/titled n}")

fn said db line
  print line .> (_ -> effect db)
kanso run spec/db/associated
note 1: ["a" "b"]
note 2: ["c"]
page 2: note: second

a page at a time

a list that may grow is read a page at a time, as Pagy reads one for a Rails app. note/paged db number per answers a models/page: the records on the page, its number, and whether another page follows. the read policy is asked about the rows of that page, so a page may show fewer than per. underneath it is models/paged db sql params number per, which runs a query with a limit and an offset after its order by. it asks for one row more than a page holds to learn whether another page follows, and leaves that row off. models/page_number reads the page a query string asks for, and anything that is not a whole number of 1 or more is the first page, so a link that has been edited by hand still shows a list.

models/models.kso
# Page `number` of what `sql` selects, `per` rows to a page, as Pagy reads
# one for a Rails app. The query is asked for one row more than a page
# holds, which says whether another page follows, and that row is not shown.
# `sql` ends where a limit may follow it, after its `order by`.
pub fn paged db sql params number per
  n = length params
  limited = "{sql} limit ${n + 1} offset ${n + 2}"
  asked = list/concat params ["{per + 1}" "{(number - 1) * per}"]
  pg/query db limited asked .> (r -> effect (page_of r.rows number per))

fn page_of rows number per
  on_it = list/to_list (list/take rows per)
  page on_it number (length rows > per)

# The page a query string asks for: its whole number when that is 1 or
# more, and 1 for anything else, a missing `page` among them.
pub fn page_number asked
  at_least_one (text/to_int asked)

fn at_least_one none
  1

fn at_least_one n
  if (n < 1) 1 n

a scaffold's index lists its rows this way, 25 to a page, as the generators guide shows.

a resource that lists another's records and one that shows its parent would import each other, and kanso refuses an import cycle. keeping each model in a module of its own, apart from the resource's actions, avoids it: both resources import both models, as the notebook's pages resource imports note beside its own page.
