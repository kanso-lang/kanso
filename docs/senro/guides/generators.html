senro guides

generators

senro's generators write the files an app starts from, as Rails' do. new writes an app that serves a home page, and scaffold adds a resource to it: a table, a model, the seven actions and three views. this guide runs both and reads what they write. the result is examples/notebook in senro's repository. senro's specs write it again on every run and compare the two, and they serve it on both engines and make, change and remove a note through it, so the files on this page are what the generators write today.

running them

the generators are run with senro, senro's command, which sits in the bin directory of senro's repository. with that directory on your PATH, senro new writes an app where you are, and every other command runs from inside the app. the files it writes import senro by the path from the app to senro's own directory, so an app beside a copy of senro imports ../senro/models; the notebook, two directories down in senro's own repository, imports ../../models. the command line guide covers the rest of the command.

shell
$ senro new notebook
  create notebook/main.kso
  create notebook/home.kso
  create notebook/home_test.kso
  create notebook/migrations/.keep
  create notebook/views/layout.kata
  create notebook/views/home.kata
$ cd notebook
$ senro generate scaffold note title:text pages:int cover:attachment
  create ./note.kso
  create ./notes.kso
  create ./views/notes_index.kata
  create ./views/notes_show.kata
  create ./views/notes_form.kata
  create ./notes_test.kso
  create ./given.kso
  create ./migrations/20261111180512_create_notes.kso
  change ./main.kso
$ senro generate scaffold page body:text note:references
  create ./page.kso
  create ./pages.kso
  create ./views/pages_index.kata
  create ./views/page_shown.kata
  create ./views/page_form.kata
  create ./pages_test.kso
  change ./given.kso
  create ./migrations/20261111180513_create_pages.kso
  change ./main.kso

each line names a file and what happened to it. scaffold writes its migration as a file of its own, a spec of the resource beside its module, and the resource's map in given.kso, which the specs make rows from; the testing guide covers both. it changes one file that new wrote, the entry, which gains the resource's import. it writes nothing over a file that is there already, and it stops before writing anything at all when a field is not one it can read.

shell
$ senro generate scaffold note title:text
generate: ./notes.kso is there already
$ senro generate scaffold book title:words
generate: cannot read `title:words`: a field is name:text, name:int, name:references or name:attachment

a field is name:text, name:int, name:references or name:attachment. the first two are the kinds a posted form's value reads back as without a parser of its own. the third nests the resource under another, as described below under a resource under another. the fourth is a file, kept as the uploads guide describes, and its column holds the key the file was kept under. a text column takes the value as it was typed. Postgres reads an integer column's value from its digits and refuses any other, so the scaffold gives each int field a rule, below, that turns a value Postgres would refuse into a problem shown on the form. :uniq after a kind, as in email:text:uniq, adds a unique index on the column, as Rails' generator reads it, and the models guide describes what a write answers when a value is taken. a field's name is a lowercase letter and then letters, digits and underscores, at most 24 of them, so that every line the scaffold writes fits in 80 columns.

the entry

new writes an entry that connects, migrates and serves. it reads the database from the environment as libpq does, so the same app runs on a laptop and on a host that sets PGHOST and the rest. its migrations are recorded under the app's name, which is the last part of its path.

examples/notebook/main.kso
# The database comes from PGHOST, PGPORT, PGUSER, PGDATABASE and
# PGPASSWORD, as libpq reads them, so the app runs wherever its host
# sets them.
connected = pg/from_env

the rest of the entry new writes is two lines. derive app/conventions runs every convention senro has an app follow: the views, the tables and their models, the routes, the jobs and the data providers. app/run runs the migrations, compares the database with the schema the app derives, and serves on the port PORT names, 3000 when it is unset. a worker runs beside the server for the app's jobs once it has one, and another sends its mail once it has a mailer. each scaffold adds the imports of the two modules it made, among the app's own imports and in order, so the entry reads as if it had been written by hand. the whole entry, as it stands after accounts are added, is shown below under accounts and signing in.

the migration

scaffold writes the migration that makes the resource's table as a file under migrations, named for the moment it was written and for what it does.

examples/notebook/migrations/20261111180512_create_notes.kso
import "../../../models"

pub create_notes = models/create_table "notes" [
  (models/column "title" "text")
  (models/column "pages" "integer")
  (models/column "cover" "text not null default ''")
]

the table ends with models/created_at and models/updated_at, as a Rails scaffold ends with t.timestamps. a resource nested under another needs a second change, the key to its parent, so its migration is a list: the table under a name of its own, then the key.

examples/notebook/migrations/20261111180513_create_pages.kso
import "../../../models"

pub create_pages = [
  pages_table
  (models/add_foreign_key "pages" "note_id" "notes")
]

pages_table = models/create_table "pages" [
  (models/column "body" "text")
  (models/column "note_id" "integer not null")
]

the files run in the order of their names, so the notes are made before the pages that point at them. the migrations guide says how they are ordered, run and recorded, and how senro generate migration writes one that changes a table that is there.

the model

scaffold writes two modules for a resource, and note.kso is the model. it is named for one row of the table, as a Rails model is named in the singular, and the models guide says how that gives it its record: the derivation declares note here with a field for each column of notes, so the module never lists them. the three policies let anyone write, which suits a first run and nothing after it. problems holds the model's rules; the scaffold writes one for each int field, and models/whole_number is broken by anything an integer column would refuse.

examples/notebook/note.kso
import "../../models"

# A note is a row of the `notes` table. This module is named for it, so the
# models derivation declares `note` here with a field for each column and
# answers for the table by this module's name: `note/find db id`,
# `note/paged db number per`, `note/create db fields` and the rest.
#
# Anyone may make, change and remove a note. The models module asks these
# before it writes; narrow them to the visitors who should.
pub fn create? _ _
  true

pub fn update? _ _
  true

pub fn destroy? _ _
  true

# What makes a note fit to keep: each number is one its column takes.
pub fn problems r
  models/problems [(models/whole_number "pages" r.pages)]

the derivation also writes the table's reads and writes into this module, and the rest of the app calls them by its name: note/find db id, note/paged db number per, note/create db fields. the models guide lists them all.

with a module of its own, the model can use the names the resource uses: notes/create is the action, and note/create is the write it calls. a second resource can also import the model without the actions. pages.kso, below, imports note to ask whether a page's note is there.

the resource

notes.kso is the resource. its seven actions are the ones a Rails scaffold writes, and the routing guide says how each name places it. each reads or writes through the model by name, and the module holds no SQL. the db an action is handed knows who is signed in, so note/create, note/update and note/destroy ask the model's policies about that visitor, and check its rules, before anything is written.

examples/notebook/notes.kso
import "../../models"
import "../../routes"
import "../../web"
import "./note"
import "./views"
import "std/list"
import "std/net/http"

pub fn index req db
  number = models/page_number (web/value (web/query req) "page")
  note/paged db number per_page .> (p -> effect (listing req p))

# How many rows a page of the list shows.
per_page = 25

pub fn show req db id:int
  note/find db id .> (r -> effect (shown req r))

pub fn new req _
  path = routes/path_to "notes/create"
  effect (form req path "POST" blank {} 200)

pub fn create req db
  given = sent (web/input req)
  note/create db given .> (w -> effect (made req w))

pub fn edit req db id:int
  note/find db id .> (r -> effect (editing req id r))

pub fn update req db id:int
  given = picked (web/input req)
  note/update db id given .> (w -> effect (changed req id w))

pub fn destroy _ db id:int
  note/destroy db id .> (w -> effect (gone w))

index shows a page of notes at a time. models/page_number reads the page the query string asks for, and anything that is not a whole number of 1 or more reads as the first page. note/paged reads that page of the notes, oldest first. it asks for one row more than per_page so that it knows whether another page follows, as Pagy does for a Rails app, and answers the page's records, its number, and whether there is more. the list links the page before and the page after, each only when there is one.

examples/notebook/notes.kso
fn listing req p

  return web/json 200 mapped if web/wants_json? req
  page = views/notes_index_view p.rows p.number p.more

senro's spec makes a note, asks for it as JSON, changes it, and asks for the list the same way. ids and times change from run to run, so the spec prints each id as N and each time as T:

spec/generate/served.out
it as json: {"cover":"","created_at":"T","id":N,"pages":12,"title":"First","updated_at":"T"}
the list as json: [{"cover":"","created_at":"T","id":N,"pages":13,"title":"Renamed","updated_at":"T"}]

a form with a file in it is sent as multipart/form-data, and senro keeps the file and hands the action its key in the field's place. a file input left empty sends an empty value, and update leaves it out of the change, so a note keeps its cover when it is edited without choosing another. create takes every field, an empty cover among them.

examples/notebook/notes.kso
fn picked f
  without_empty_files (sent f) ["cover"]

fn sent f
  {
    "cover":(web/value f "cover")
    "pages":(web/value f "pages")
    "title":(web/value f "title")
  }

fn without_empty_files given names
  list/fold names given (m n -> if (m[n] == "") (delete m n) m)

what each write answers decides the response. a record that breaks a rule comes back as models/invalid, and the form is shown again with what was typed and a 422. a write a policy refuses is a web/denied, and a row that is not there is a web/absent; web/refusal answers them with a 403 and a 404. anything else is the record as stored, and the action redirects to it.

examples/notebook/notes.kso
fn made req w:models/invalid
  path = routes/path_to "notes/create"
  form req path "POST" (filled w.record) w.problems 422

fn made _ w:web/denied
  web/refusal w

fn made _ w
  web/redirect (routes/path_to "notes/show" w.id)

fn changed req id w:models/invalid
  path = routes/path_to "notes/update" id
  form req path "PATCH" (filled w.record) w.problems 422

fn changed _ _ w:web/denied
  web/refusal w

fn changed _ _ w:web/absent
  web/refusal w

fn changed _ id _
  web/redirect (routes/path_to "notes/show" id)

fn gone w:web/denied
  web/refusal w

fn gone w:web/absent
  web/refusal w

fn gone _
  web/redirect (routes/path_to "notes/index")

the views

three templates: the list, a note, and the form that makes and changes one. the form takes the path it is sent to and the method, so new sends it to /notes as a POST and edit to the note's own path as a PATCH, which the hidden _method field carries. each field shows the problem a rule found with it, if there was one.

examples/notebook/views/notes_form.kata
takes path method fields problems
header
  h1 Note
  p.lede
    a href=(path_to "notes/index") All notes
form method="post" action=path enctype="multipart/form-data"
  input type="hidden" name="_method" value=method
  label
    | title
    input name="title" value=fields["title"]
  if problems["title"] != none
    p.problem = problems["title"]
  label
    | pages
    input name="pages" value=fields["pages"]
  if problems["pages"] != none
    p.problem = problems["pages"]
  label
    | cover
    input type="file" name="cover"
  if fields["cover"] != ""
    p.kept Leave it empty to keep the file it has.
  button Save

a resource under another

a field written name:references nests the resource under another, as Rails' generator reads it. the second scaffold above makes pages that belong to a note. it writes a model, page.kso, and a resource, pages.kso, as the first did for notes. its migration holds two changes: pages_table makes the table with a note_id column that may not be empty, and the call of models/add_foreign_key has Postgres refuse a page whose note is not there and remove a note's pages along with the note.

each of the resource's actions takes the note's id right after the database, which is how the routing guide places a nested resource: pages/index answers GET /notes/:note_id/pages, and pages/show GET /notes/:note_id/pages/:id.

examples/notebook/pages.kso
# A row of `pages` belongs to a note, so each action takes the note's id and
# the routes nest under it: `index` answers GET /notes/:note_id/pages. A row
# is found only under its own note, and a note that is not there has none to
# list or make.
pub fn index req db note_id:int
  number = models/page_number (web/value (web/query req) "page")
  asked = page/paged db "note_id" note_id number per_page
  listing_of = (p -> effect (listing req note_id p))
  within db note_id (asked .> listing_of)

pub fn show req db note_id:int id:int
  under db note_id id .> (r -> effect (shown req r))

# `then` when the note is there, and a 404 when it is not.
fn within db id then
  note/find db id .> (found -> held found then)

fn held none _
  effect http/not_found

fn held _ then
  then

# The row with this id under this note, or none.
fn under db note_id id
  page/find db id .> (r -> effect (owned note_id r))

fn owned _ none
  none

fn owned note_id r
  if ("{r.note_id}" == "{note_id}") r none

page/paged db "note_id" note_id number per_page reads one page of the pages whose note_id is the note's. under finds a page by its id and keeps it only when it belongs to the note the path names, so /notes/1/pages/7 finds nothing when page 7 belongs to note 2. listing a note's pages and making one first ask note/find whether the note is there, and answer 404 when it is not.

the note's resource must be there before the pages are generated, a resource nests under one parent, and a reference's name is at most 12 characters, so the lines the scaffold writes still fit in 80 columns.

shell
$ senro generate scaffold chapter body:text volume:references
generate: . has no volumes to nest chapters under
$ senro generate scaffold book note:references page:references
generate: cannot read `page:references`: a resource nests under one parent

a resource with no pages

resource writes an API over a model, as rails g scaffold --api does. it takes a name and fields as scaffold does and writes the model and its migration the same way. where scaffold writes seven actions and three views, resource writes five actions that answer JSON.

shell
$ senro generate resource reading title:text minutes:int
  create ./reading.kso
  create ./readings.kso
  create ./readings_test.kso
  change ./given.kso
  create ./migrations/20261111180515_create_readings.kso
  change ./main.kso

the five actions are the ones the routing convention places without a form: the list, one row, and the three that write.

examples/notebook/readings.kso
# The readings, as an API: each action answers JSON, and `create` and
# `update` read a posted form or a JSON object (`web/input`).
pub fn index req db
  number = models/page_number (web/value (web/query req) "page")
  reading/paged db number per_page .> (p -> effect (listing p))

# How many rows a page of the list holds.
per_page = 25

pub fn show _ db id:int
  reading/find db id .> (r -> effect (shown r))

pub fn create req db
  given = taken (web/input req)
  reading/create db given .> (w -> effect (made w))

pub fn update req db id:int
  given = taken (web/input req)
  reading/update db id given .> (w -> effect (changed w))

pub fn destroy _ db id:int
  reading/destroy db id .> (w -> effect (gone w))

create and update read what was sent with web/input, which answers the fields of a posted form or of a JSON object, by the request's content type. taken keeps the fields the resource names and drops the rest, so a request cannot set a column the generator was not told about. an update changes the fields a request sends and leaves the others as they are.

examples/notebook/readings.kso
# The fields a request may set. One it does not send is left as it is.
fields = ["minutes" "title"]

fn taken sent
  list/fold fields {} (acc n -> kept acc n sent[n])

fn kept acc _ none
  acc

fn kept acc n v
  put acc n v

each write answers by what came back from the model. a row that breaks a rule is answered 422 with the problem of each field, and a write the model's policy turns down, or one for a row that is not there, is answered as web/refusal answers it.

examples/notebook/readings.kso
# A row that breaks a rule answers 422 with the problem of each field.
fn made w:models/invalid
  web/json 422 w.problems

fn made w:web/denied
  web/refusal w

fn made w
  web/json 201 (reading/reading_attributes w)

a resource's fields are text and int. a file or a field that refers to another table is scaffold's to write, and resource says so and writes nothing when it is given one.

accounts and signing in

generate authentication adds accounts to an app, as Rails 8's authentication generator does, with a sign-up page as Devise's registerable adds. it writes seven modules and five views, the migration that makes a users table, and changes the entry.

shell
$ senro generate authentication
  create ./account_mailer.kso
  create ./confirmations.kso
  create ./registration.kso
  create ./resets.kso
  create ./session.kso
  create ./session_test.kso
  create ./unlocks.kso
  create ./user.kso
  create ./views/confirm_offered.kata
  create ./views/door.kata
  create ./views/reset_asked.kata
  create ./views/reset_chosen.kata

a user is an address and a digest of the password, and user.kso is its model. the file holds one policy, and the models derivation declares the record from the table's columns.

examples/notebook/user.kso
# A user, as the `users` table stores them: the address they sign in with
# and a digest of the password. The password itself is never stored. This
# module is named for the record, so the models derivation declares `user`
# here with a field for each column and answers for the table by this
# module's name.
#
# Anyone may make an account, as Devise's registerable lets them. A reset
# link sets a password as the app, so no policy lets a viewer change one.
pub fn create? _ _
  true

five resources work on the model. registration makes a user, at /registration/new, and mails a link that confirms its address. session signs in at /session/new and out with DELETE /session. resets mails a link that sets a new password, confirmations follows the link that confirms an address, and unlocks follows the one that unlocks an account. account_mailer writes the three letters. the resources read and write through user by name, with user/find_by, user/find and user/create, and hold no SQL. nobody is signed in when a mailed link is followed, so the resource behind it writes as the app: user/update (models/as_app db) id { "digest":d } sets a new password. these are the guestbook's modules with less in them: an account is known by its address alone, and there is no page for changing a password. the sessions guide explains each part, and the files are the app's own to change.

examples/notebook/session.kso
# The key that signs every session, which senro reads by its name.
# `generate authentication` made it at random for development; a deployed
# app sets `SENRO_SECRET` instead, which senro reads in its place, so the
# real one stays out of the repository. Changing it signs every visitor out.
pub secret = "made at random by generate authentication"

pub without_sign_in = ["create" "new"]

# What a sign-in rests on: the digest the account keeps now. A new password
# changes it, so a password reset signs out every session made before it.
pub signed_against = (db email -> user/find_by db "email" email .> kept_of)

the secret that signs every session is 32 random bytes the generator made when it ran, so two apps never share one. keep it out of any repository the public can read; changing it signs every visitor out.

an account signs in once its address is confirmed, as Devise's confirmable asks. the sign-in locks an account after five wrong passwords in a row, for an hour or until the link mailed to its address unlocks it, as Devise's lockable does, and counts and stamps each sign-in, as its trackable does. the counting is senro's, in the accounts module; the generated file holds the two numbers and says what each outcome answers.

examples/notebook/session.kso
# Five wrong passwords in a row lock an account for an hour, or until the
# link mailed to its address unlocks it, as Devise's `lockable` does. A
# right password ends the run of wrong ones, and each sign-in is counted
# and stamped, as its `trackable` does (`accounts`).
pub locks_after = 5

pub locked_minutes = 60

# What a sign-in comes to is `accounts`' to decide: the password checked,
# the lock kept, and a right password counted and stamped. A locked account
# tells only the holder of the right password that it is locked, and the
# wrong password that locks it mails the link that unlocks it. The right
# password for an address not yet confirmed sends the confirmation again.
fn entered req db email a password t
  model = user/user_model
  accounts/attempt req db model a password locks_after locked_minutes t
    .> (v -> answered req db email a v)

fn answered req db email a v
  return signed req a if v.outcome == "signed"
  return unconfirmed req db email a if v.outcome == "inactive"
  return shut req email if v.outcome == "locked"
  return effect (refused req email) if v.stamp == ""
  account_mailer/unlock req db a.id a.email v.stamp
    .? (u -> io/write_err "no unlock mail: {u.reason}\n")
    .> (_ -> effect (refused req email))

a locked account answers a wrong password with the same 422 as ever, and tells only the holder of the right one that it is locked. the migration the generator writes for users holds the columns accounts/attempt keeps, which accounts/columns lists, confirmed among them. senro's spec drives the generated app to a lock and follows the mailed link that opens it:

# PGPASSWORD, as libpq reads them, so the app runs wherever its host
# sets them.

the entry now serves its routes through web/requiring_sign_in, so every action asks for a sign-in unless its module lists it in without_sign_in. that includes the home page and the notes, as in a Rails 8 app after the generator runs. a visitor who has not signed in is sent to /session/new, and back to the page they asked for once they have. the mail worker new set beside the server sends the letters account_mailer queues; the background jobs guide covers it.

senro's spec serves the generated app on both engines and uses it as a visitor would. it makes an account, is refused until it confirms the address through the mail the app writes, and follows the used link again to see it refused:

making an account and confirming its address
making an account: 303 to /session/new
the same address again: That address has an account.
signing in before confirming: 403 Confirm your address first. We have sent the link again.
its confirmation page: 200
confirming: 303 to /session/new Your address is confirmed. Sign in with it.
the link again: 303 to /session/new That link has expired or was used. Sign in to have it sent again.
signing in: 303 to /

it then works with notes and pages, signs out, and resets the password through the mail.

resource is covered above. model takes what scaffold takes and writes the model alone: the module named for the record and the migration that makes its table. controller takes a plural name and the actions it should have, each one of the seven the routing convention places, and writes a module with those actions and a view for each that shows a page. migration writes a migration from its name, as the migrations guide describes. mailer takes a name and its letters and writes <name>_mailer.kso, with a function for each letter that composes it and queues it for the worker. job takes a name and writes <name>_job.kso, whose perform the second worker calls; the background jobs guide covers how a job is found and queued.

a generator senro does not ship is a kanso program at generators/<name>.kso, in the app or beside a library the app's entry imports by path. senro generate <name> runs it in the app's directory with the words that followed, and the list above shows it with where it was found. senro's own are looked for first, so one from outside cannot take the place of scaffold.

after generating

three things are worth doing before an app goes anywhere. narrow the policies to the visitors who should write. add the model's other rules to problems, as the models guide describes, such as a title that may not be blank. and replace the home page, which says only that the app exists.
