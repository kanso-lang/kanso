JavaScript

most of a senro app's pages need no JavaScript of its own. the page script morphs each answer into the live page, and a component's actions run in the browser as wasm. a chart, a map or a date picker is different: it is a JavaScript library, and something has to call it. in senro that something is a small module the app writes. the app's views render the data as attributes on an element, the module reads them and drives the library, and when the library has something to report it dispatches an event that a component's action answers. kanso has no call into JavaScript, so a component stays a function from its state to HTML and runs on every engine (kanso#2284).

this guide covers where an app's modules live, how senro installs and vendors packages, how a library keeps its element when the page changes, and how a library's event reaches an action. the pantry's chart is the running example.

the app's modules

an app's JavaScript lives in javascript/, and javascript/application.js is the entry. a module imports a package by its name and another of the app's modules by its path without .js, with a directory's name standing for its index.js:

examples/pantry/javascript/application.js
// The pantry's JavaScript: the adapter that draws the shelf's chart.
import "chart";

the layout needs nothing new. senro's page script, which every layout already loads from /senro.js, carries the app's import map, asks for each module the page needs at once, and imports application.

installing packages

senro manages packages the way jspm-rails does for a Rails app, with jspm's generator. install the generator beside the app once, as a development dependency, so the app pins its version like any other:

npm install --save-dev @jspm/generator
senro js install
      traced  javascript/application.js
    vendored  2 modules from ga.jspm.io
       wrote  importmap.json

the install traces the entry and every other module in javascript/, finds every module they reach across whole dependency trees, and downloads each from jspm.io, with its source map, into vendor/javascript/. it writes the import map, and the list of modules a page loads at once, to importmap.json. commit both. a deployed app serves the vendored files itself, so it needs neither Node nor jspm.io. the pantry's map names its two modules and the one package they reach:

{
  "imports": {
    "application": "/javascript/application.js",
    "chart": "/javascript/chart.js"
  },
  "scopes": {
    "/": {
      "chartist": "https://ga.jspm.io/npm:chartist@2.2.1/dist/index.js"
    }
  },
  "preload": [
    "/javascript/application.js",
    "/javascript/chart.js",
    "https://ga.jspm.io/npm:chartist@2.2.1/_/BUd082zi.js",
    "https://ga.jspm.io/npm:chartist@2.2.1/dist/index.js"
  ]
}

the map keeps jspm.io's URLs, which is what makes it jspm's lockfile. senro rewrites them to /vendor/javascript/ga.jspm.io/npm/… as it serves the page script. a vendored module's path names its package's version, so the server tells the browser to keep it for a year. one of the app's own modules is checked against its ETag on each page load, so an edit reaches the next page.

versions

an install keeps every version the previous importmap.json holds. to move a package installed only through jspm, delete its entries from the map and install again. a package npm installed takes the version package-lock.json holds at its top level instead, so a Dependabot bump reaches the map at the next install, and the package's stylesheets and fonts are in node_modules at the same version as its JavaScript.

npm installs a second version of a package when its dependents' ranges do not meet. an import map holds one version of each package, so the install uses the top-level version everywhere and prints a warn line naming the package and both versions.

a module of the app's that has a package's name is refused, since an import of that name could mean either:

senro js: javascript/chartist.js has the name of the package chartist; rename one of them

checking in CI

senro js check traces and downloads again and writes nothing. it fails when an install would change importmap.json, and when a file under vendor/javascript/ is missing, differs from what jspm.io serves, or is one the trace no longer reaches. run it in CI and a hand edit to vendored code cannot land:

     changed  vendor/javascript/ga.jspm.io/npm/chartist@2.2.1/dist/index.js
         run  senro js install

a library's element

the page script morphs each new page into the live one, matching elements and copying the server's attributes and children onto them. a chart draws its own children, so the morph would erase it. an element marked data-owned-by keeps its children through the morph, and its attributes are still kept current, which is how the library hears of new data. the pantry's shelf writes the names and counts it charts onto such an element:

examples/pantry/views/shelf.kata
.chart data-owned-by="chart" data-names=names data-counts=counts

the chart's module draws into each such element when it appears and draws again when data-counts changes. a MutationObserver watches for both, so the module needs no word from senro:

examples/pantry/javascript/chart.js
import { BarChart } from "chartist";

const charts = new WeakMap();

const data = (el) => ({
  labels: el.dataset.names ? el.dataset.names.split("\n") : [],
  series: [el.dataset.counts ? el.dataset.counts.split(" ").map(Number) : []],
});

const options = { axisY: { onlyInteger: true, low: 0 }, height: "10rem" };

const drawn = (el) => {
  const chart = charts.get(el);
  if (chart) chart.update(data(el));
  else charts.set(el, new BarChart(el, data(el), options));
};

the rest of the file finds the elements and watches them. spec/browser/pantry.mjs reads the chart's bars at every step of its run and waits until they show the counts the list shows. with the morph's rule taken out, it times out at the first change that leaves the counts alone, because the morph erased the chart and nothing redrew it.

a library's events

the way back from the library is an event. a template binds any event as it binds a click: on-click=more writes data-on-click, and on-change=typed writes data-on-change. the page script listens for every event name a binding on the page names. an action that names a parameter value is handed the event's value as text, before its state: a field's value for an event the browser fires, the detail of a CustomEvent, and "" for a click. so a library's module reaches a component by dispatching an event on an element inside it:

el.dispatchEvent(new CustomEvent("change", { bubbles: true, detail: 2 }));

the pantry's planner binds its number field this way:

examples/pantry/planner/view.kata
  input.meals type="number" min="0" aria-label="meals" on-change=typed
examples/pantry/planner/planner.kso
pub fn typed value _
  planned (counted (text/to_int value))

typed takes no req, db or viewer, so it runs in the browser. the pantry's browser spec sets the field by typing 6 and then by dispatching the event above, and the planner shows 6 and then 2 with no request to the server. an action that also names req, db or viewer runs on the server, and the page posts the value beside the state. a value with a line break in it arrives whole, since it travels as a JSON string.

what is not here

there is no bundler and no build step: the browser loads the modules their authors wrote, and caches each on its own. there is no call from kanso into JavaScript. kanso#2284 weighed one and chose the boundary in this guide. each action runs in a fresh instance of the app's module, so nothing in kanso outlives an event to hold a chart, and a component that called JavaScript could no longer run its specs on the interpreter.
