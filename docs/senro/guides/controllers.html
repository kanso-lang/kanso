controllers and actions

a Rails controller is a class whose methods are actions. in senro it is a module: notes.kso holds the actions for notes, and each is a pub function named for what it does. the routing guide covers how an action's name places it at a path. this guide covers what an action is handed, how it reads what the browser sent, and the answers it can give. the examples are from the module that senro generate scaffold note title:text pages:int cover:attachment writes.

what an action is handed

an action takes the request and a database session, and an action on one row takes the row's id after them. it answers an effect that yields the response.

examples/notebook/notes.kso
pub fn show req db id:int
  note/find db id .> (r -> effect (shown req r))

pub fn new req _
  path = routes/path_to "notes/create"
  effect (form req path "POST" blank {} 200)

pub fn create req db
  given = sent (web/input req)
  note/create db given .> (w -> effect (made req w))

pub fn destroy _ db id:int
  note/destroy db id .> (w -> effect (gone w))

req is the request as kanso's std/net/http parsed it. req.method and req.path are text, req.headers is a map keyed by each header's name in lowercase, and req.body is what a form posted. db is a Postgres session the server lends the action from its pool and takes back when the action has answered, so two requests never share one. an action names a parameter _ when it has no use for it, as new does with the session.

an id:int is the number in the path. a request for /notes/seven is answered 404 before the action is called, so show never checks that its id is a number.

reading what was sent

a form posts its fields in the request's body. web/form req.body reads them into a map from each field's name to its value, and web/value reads one field from that map, answering "" for a field the form did not send.

examples/notebook/notes.kso
fn sent f
  {
    "cover":(web/value f "cover")
    "pages":(web/value f "pages")
    "title":(web/value f "title")
  }

sent names each field the action takes, which is the job Rails gives to strong parameters. a field the form was not meant to carry is never read, so a visitor who adds one to the request changes nothing. the values are still text as the visitor typed them; the model's rules decide whether they will do, as the models guide describes.

a query string is read the same way. web/query req is the map, so /notes?page=2 gives the list its page number.

examples/notebook/notes.kso
pub fn index req db
  number = models/page_number (web/value (web/query req) "page")
  note/paged db number per_page .> (p -> effect (listing req p))

# How many rows a page of the list shows.
per_page = 25

a form with a file in it arrives in a different encoding, and the uploads guide covers how an action reads one.

answering with a page

an action that shows a page asks the app's views module to draw it. views/answer req page answers 200, and views/answer_as req code page answers with a status of the action's choosing. the page is usually a view placed in the layout.

examples/notebook/notes.kso
# The form a note is made and changed with: its fields as typed, and the
# problem with each, if any.
fn form req path method fields problems code
  page = views/notes_form_view path method fields problems
  views/answer req code "Note" page

the scaffold shares one form between new and edit, and shows it again with a 422 when a write is refused. a program that posts the form learns from the status that it was not accepted, without reading the page.

redirecting, and leaving a notice

an action that changed something answers web/redirect path. that is a 303, which tells the browser to ask for the path with a GET, so reloading the page that follows posts nothing a second time.

examples/notebook/notes.kso
fn made req w:models/invalid
  path = routes/path_to "notes/create"
  form req path "POST" (filled w.record) w.problems 422

fn made _ w:web/denied
  web/refusal w

fn made _ w
  web/redirect (routes/path_to "notes/show" w.id)

web/noticed wraps an answer and leaves a message for the request after it, as redirect_to path, notice: message does in Rails. the next action reads it with web/notice req and hands it to its view, and the server forgets it once that request is answered. signing out of the generated app leaves one.

examples/notebook/session.kso
# Signing out keeps the rest of the session and forgets the sign-in.
pub fn destroy req _
  s = web/signed_out (web/session req)
  r = web/redirect (routes/path_to "session/new") "Signed out."
  effect (web/kept req r s)

answering JSON

the same action can answer a program. web/wants_json? req is true when the path ends in .json or the request's Accept header names application/json, and web/json status value answers a map or a list of maps. the route is matched without the .json, so /notes/3.json reaches the action /notes/3 does.

examples/notebook/notes.kso
fn listing req p
  as_json = note/note_attributes
  mapped = list/to_list (list/map p.rows as_json)
  return web/json 200 mapped if web/wants_json? req
  page = views/notes_index_view p.rows p.number p.more
  views/answer req 200 "Notes" page

note/note_attributes is the row as a map of its columns, which the models derivation writes for every model.

when a write is refused

a model's write answers the row it wrote, or one of three other things. models/invalid means a rule failed, and carries the record as sent and the problem with each field. web/denied means the model's policy said this viewer may not make the change. web/absent means the row is not there. an action has an arm for each it can meet, and the last arm is the write that worked.

examples/notebook/notes.kso
pub fn update req db id:int
  given = picked (web/input req)
  note/update db id given .> (w -> effect (changed req id w))

fn changed req id w:models/invalid
  path = routes/path_to "notes/update" id
  form req path "PATCH" (filled w.record) w.problems 422

fn changed _ _ w:web/denied
  web/refusal w

fn changed _ _ w:web/absent
  web/refusal w

fn changed _ id _
  web/redirect (routes/path_to "notes/show" id)

web/refusal turns a denial into a 403 and an absence into a 404. an action may also answer either value as it stands, and the server writes the same response for it. a read that finds no row answers none, and the action answers http/not_found.

examples/notebook/notes.kso
fn shown _ none
  http/not_found

fn shown req record
  attributes = note/note_attributes record
  return web/json 200 attributes if web/wants_json? req
  page = views/notes_show_view record
  views/answer req 200 "Note" page

what a module can say about its actions

three declarations in a module change how its actions are reached, and each has its own guide.

  • rate_limits maps an action to how often one client may call it, such as { "create":"10 per 3 minutes" }. a call past the limit is answered 429 without reaching the action. see sessions and sign-in.
  • without_sign_in lists the actions a visitor may reach before signing in, in an app whose entry asks for a sign-in everywhere else. see sessions and sign-in.
  • admits action viewer db says who may reach each action, and is asked once for a page and the data it loads. see authorization.

what the server does around an action

the server writes a line for each request it answers: the method, the path, the status and how long the answer took.

what the server prints
GET /notes 200 in 2ms
POST /notes 422 in 2ms
POST /notes 303 in 2ms
GET /notes/1 200 in 1ms
GET /notes/1.json 200 in 3ms
GET /resets/:token/edit 200 in 2ms

a path segment that is a signed token, such as the one in a password reset link, is written as :token, so a log never holds a link someone could follow.

an action that fails with an error it did not plan for does not stop the server. the reason goes to standard error, the browser is answered 500, and the next request is served as usual. an action that answers something that is no response is reported the same way, so a missing arm shows up in the log the first time it is reached.
