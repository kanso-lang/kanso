the name
senro (線路) is japanese for a railway line: the track a train runs on. Rails gave web development its conventions; senro lays the same track for a language whose compiler can check them.
an app

a guestbook, whole

senro's first app is a guestbook: visitors make an account, sign in, sign the book and remove what they signed. These are its own files. The panel above is its schema.

A model is a module named for one row of its table, holding the rules for the table's records. senro declares the record itself, signature, from the signatures table. The policies say who may create and remove a signature, and problems says what makes one unfit to keep.

examples/guestbook/signature.kso
import "../../models"
import "std/text"

# A signature is a row of the `signatures` table. This module is named for
# the record, so the models derivation declares `signature` here with a
# field for each column and answers for the table by this module's name.
#
# Only the person who signed an entry may remove it. `signature/destroy`
# asks this policy before it deletes anything, and nothing else in the
# guestbook removes a signature.
pub fn destroy? viewer s
  s.name == viewer

# Anyone may sign the book.
pub fn create? _ _
  true

# A signature needs a name and a message, and a message short enough to
# read at a glance.
pub fn problems s
  models/problems [
    (models/rule "name" (text/trim s.name == "") "Say who you are.")
    (models/rule "message" (text/trim s.message == "") "Say something.")
    (models/rule "message" (length s.message > 280) "Keep it under 280.")
  ]

An action is a public function, and its name places it. entries/index answers GET /entries and entries/create answers POST /entries. Nothing else declares a route. An action reads and writes through the model by name and writes no SQL: signature/newest db is the book with the latest signature first, and signature/create db f asks the policy and checks the rules before it stores anything.

examples/guestbook/entries.kso
import "../../models"
import "../../web"
import "./removal"
import "./signature"
import "./views"
import "std/list"

# The session says who is signed in, and carries a notice across the
# redirect that follows a signature or a sign-in; the page that shows the
# notice clears it.
pub fn index req db
  s = web/session req secret
  signature/newest db .> (book -> shown req book s (filled "" {}) 200)

# A development secret. A deployed guestbook signs its sessions with its own.
pub secret = "the guestbook's development secret"

# A signature is made through its model, whose rules decide whether it is
# fit to keep. It is signed with the name of the account signed in. The
# fields go to Postgres as parameters, so what a visitor types is stored as
# text and never read as SQL.
pub fn create req db
  viewer = web/viewer req secret
  f = put (web/form req.body) "name" viewer
  signature/create db f .> (w -> signed req db w)

running

the pantry, in a browser

senro's second example app keeps a shelf of things with counts and plans the week's meals. the meal count is a component whose actions run in the browser, in the app's own kanso compiled to wasm, so the − and + buttons send nothing to the server. the check button asks which starred staples the week would run short of. its action calls stock/short meals, a provider that reads the shelf through the item's model on the server, and each check is one request. the shelf's own buttons are forms the server answers, and the page script morphs each answer into the live page without a reload. the bar along the bottom is a caption added for this recording.

conventions

what senro decides

each convention is a kanso function the compiler runs during the build. what it writes is checked like code someone wrote, and kanso derived prints it.

01

routes

every route is one of a resource's seven actions, placed by its module and its name. singular resources such as /profile follow the same rule. an old URL is kept with legacy_route_aliases, which redirects to the resource's route.

02

the schema

there is no schema file. the migrations are values, folded into the schema while the app compiles, and each model's record is declared from its table's columns. when the server starts it compares the live tables with that schema.

03

models

a model's record comes from its table, and so do its reads and writes, which an action calls by the model's name. its policies and rules are the functions in its module. a write the policy refuses has no other way into the table.

04

views

templates are kata files, compiled to kanso functions. the same functions run on the server and, compiled to wasm, in the browser, so a page can be rendered from data on either side and the two agree byte for byte.

05

sessions

a session is a signed cookie. sign-in stretches passwords with PBKDF2 and salts them with the operating system's random bytes, and a session older than its limit is refused.

06

postgres

senro speaks Postgres's wire protocol in a client written in kanso, over TLS when the server asks for it. there is no C binding and no second database to abstract over.

refusals

what senro refuses

a mistake Rails reports when a request reaches it is a compile error here. a misspelled action is the plainest case.

spec/errors/misspelled_action/posts.kso
pub fn index _
  "every post"

pub fn destory _
  "gone"
kanso check
error[derive]: `destory` is not an action: name it index, new, create, show, edit, update or destroy
  --> ./posts.kso:4:8
   4 | pub fn destory _
              ^

the same goes for two routes that could answer one request, a path_to that names no route, a model field with no column, and a template that reads a field its record lacks.
